## 1. What modelling is

### Explain

You run a toy shop. Every time someone buys something you scribble a line in a notebook:

> *Ana bought 2 Red Robots and 1 Puzzle Cube at the Main Street shop on Saturday. Robots are $24.99, puzzles are $9.50.*

That's `raw_sales`. Fine for a day. After a year the notebook has 100,000 lines and three problems show up:

1. **You wrote "Red Robot" a thousand times.** Rename it and you must fix a thousand lines. Miss three and your report says you sold two different toys.
2. **You can't answer simple questions.** "How many kids live in Toronto?" means reading every line. Ben appears twice with two cities — did he move, or is one a typo?
3. **Nobody knows what a line means.** Ana's one purchase took two lines. Count lines and you'll say "6 sales" when there were 5.

**Data modelling is splitting that one messy notebook into a few tidy books so those problems go away.** That's the whole thing. Everything else is technique.

You'd naturally split it into two kinds of book:

```
   ONE MESSY NOTEBOOK                       TIDY BOOKS
 ┌───────────────────────┐        ┌──────────────────────────────┐
 │ Ana, Brampton,        │        │  THINGS THAT HAPPENED        │
 │ Red Robot, Robots,    │        │  (short lines, just numbers  │
 │ $24.99, x2,           │  ───▶  │   and codes — gets HUGE)     │
 │ Main Street, Sat...   │        │        = FACT TABLE          │
 │                       │        ├──────────────────────────────┤
 │ ...100,000 more lines │        │  THINGS THAT EXIST           │
 │                       │        │  one book of toys, one of    │
 │                       │        │  kids, one of shops.         │
 │                       │        │  Each thing listed ONCE.     │
 │                       │        │  (stays small)               │
 │                       │        │      = DIMENSION TABLES      │
 └───────────────────────┘        └──────────────────────────────┘
```

- The book of things that **happened** is a **fact table**.
- The small books of things that **exist** are **dimension tables**.

That's the core of dimensional modelling, and it covers most of what a data engineer does.

### Exercise

In one sentence each, name three problems `raw_sales` has that splitting it would fix. Don't write SQL — write English. Then write the query that proves problem #3 (the "how many sales?" one) is real.

<details>
<summary><b>Show solution</b></summary>

Three problems:
1. **Repetition** — `"Red Robot"` is stored on every sale, so renaming it means rewriting history.
2. **No list of things that exist** — a toy that sold nothing simply has no row, so you can't ask "what didn't sell?"
3. **Ambiguous rows** — a row is a *line item*, not a *sale*, so counting rows overcounts sales.

Proving #3:

```sql
SELECT count(*) AS lines, count(DISTINCT receipt_no) AS sales FROM raw_sales;
-- 6, 5
```

Ana's receipt R-001 is two lines but one sale. This is the grain mistake in its smallest possible form, and it's the same mistake that produces wrong revenue in real systems.
</details>

## 2. Grain

### Explain

Before you write a single `CREATE TABLE`, answer one question:

> **What does one row mean?**

That sentence is called the **grain**. Getting it wrong is the single most expensive mistake in data engineering. Getting it right prevents about half of all data bugs.

```
  raw_sales
  ┌──────────┬─────────────┬──────┐
  │ R-001    │ Red Robot   │  2   │ ─┐
  │ R-001    │ Puzzle Cube │  1   │ ─┴─ ONE receipt, TWO rows
  │ R-002    │ Red Robot   │  1   │
  └──────────┴─────────────┴──────┘

  ❌ "one row = one sale"          ← wrong, R-001 is two rows
  ✅ "one row = one toy on one receipt"
```

Say it out loud as a full sentence. If you can't, you don't have a grain yet.

| Table | Grain |
|---|---|
| `fct_sale_line` | one product on one receipt |
| `fct_order` | one order |
| `fct_daily_balance` | one account on one day |
| `dim_kid` | one kid |
| `dim_date` | one calendar day |

**How to check a grain in SQL.** Count rows, then count distinct combinations of the columns you *think* define a row. They must match.

```sql
SELECT count(*) AS n_rows,
       count(DISTINCT (receipt_no, toy_name)) AS n_unique
FROM raw_sales;
-- 6, 6  ✓ grain holds
```

If `n_rows` is bigger, you have duplicates, or your grain is finer than you thought.

> **Trap.** Never mix grains in one table. Put "one toy on one receipt" rows *and* "one whole receipt" rows in the same table and every sum you ever write will be wrong — and it will take someone three weeks to notice.

### Exercise

**(a)** Write the grain of `raw_sales` as one sentence, then prove it with a `count(*)` vs `count(DISTINCT ...)` check.

**(b)** Explain in one sentence why `SELECT count(*) FROM raw_sales` is the wrong answer to "how many sales did we have?", and write the query that's right.

<details>
<summary><b>Show solution</b></summary>

**(a)** *One row is one toy on one receipt.*

```sql
SELECT count(*) AS n_rows,
       count(DISTINCT (receipt_no, toy_name)) AS n_unique
FROM raw_sales;
-- 6, 6  ✓
```

If those two numbers ever diverge, either you have duplicate loads, or the same toy legitimately appears twice on one receipt — in which case your grain is actually "one *line* on one receipt" and you need a line number column.

**(b)** `count(*)` counts *lines*, not sales.

```sql
SELECT count(DISTINCT receipt_no) AS sales FROM raw_sales;
-- 5
```

Put the grain check in a test. This is genuinely the highest-value five lines of SQL in your job.
</details>

## 3. Facts and dimensions

### Explain

How do you know if a column belongs in the fact table or a dimension? Ask:

> **Does it describe something that HAPPENED, or something that EXISTS?**

```
        "Total revenue  BY category  FOR Toronto kids  IN August"
              ▲              ▲             ▲              ▲
              │              └─────────────┴──────────────┘
           FACT                      DIMENSIONS
     (numbers you add)      (words you group by / filter on)
```

| Column | Happened or exists? | Goes in |
|---|---|---|
| quantity | happened (2 were sold) | fact |
| line total | happened | fact |
| toy category | exists (robots are always robots) | dimension |
| kid's city | exists | dimension |
| shop name | exists | dimension |
| sold at | happened — but it's *when* | the link to the date dimension |

**Facts are skinny. Dimensions are wide.**

```
FACT ROW (billions of these — every byte costs money)
┌──────────┬─────────┬─────────┬──────────┬──────────┬────────────┬────────────┐
│ date_key │ kid_key │ toy_key │ shop_key │ quantity │ unit_price │ line_total │
│ 20260801 │    1    │    3    │    2     │    2     │   24.99    │   49.98    │
└──────────┴─────────┴─────────┴──────────┴──────────┴────────────┴────────────┘
   boring on purpose: just IDs and measures

DIMENSION ROW (a few thousand — extra columns are cheap, so be generous)
┌─────────┬───────────┬──────────────┬───────┬────────┬─────────┬────────────────────┐
│ toy_key │ toy_name  │ toy_category │ brand │ colour │ age_min │ is_battery_powered │
│    3    │ Red Robot │ Robots       │ ToyCo │ red    │    6    │        true        │
└─────────┴───────────┴──────────────┴───────┴────────┴────────┴─────────────────────┘
   chatty on purpose: every column is a new way to slice without asking you for help
```

### Exercise

For each column in `raw_sales`, say whether it belongs in a fact table or a dimension — and if a dimension, which one.

<details>
<summary><b>Show solution</b></summary>

| Column | Goes in |
|---|---|
| `receipt_no` | fact — *degenerate dimension* (see §6) |
| `sold_at` | fact, as `date_key` → `dim_date` |
| `kid_name` | `dim_kid` |
| `kid_city` | `dim_kid` |
| `toy_name` | `dim_toy` |
| `toy_category` | `dim_toy` |
| `toy_price` | fact as `unit_price`; **also** `dim_toy` as `list_price` |
| `quantity` | fact |
| `shop_name` | `dim_shop` |

**Price appearing in both places is deliberate, not a mistake.** `dim_toy.list_price` is what the toy *costs today*. `fct_sale_line.unit_price` is what was *actually charged*, which may differ because of a discount. Keeping both lets you answer "how much discount did we give?"
</details>

## 4. Keys

### Explain

Right now you link things by name: `toy_name = 'Red Robot'`. That's a **natural key** — it comes from the real world. Two problems: real-world things change (toys get renamed, kids change surname, shops move), and `"Red Robot"` is 9 bytes repeated a billion times.

So you give every toy a **sticker with a number on it**. The number means nothing. It never changes. That's a **surrogate key**.

```
  NATURAL KEY (sticky nametag)          SURROGATE KEY (numbered sticker)
  ┌────────────────────┐                ┌────────────────────┐
  │   "Red Robot"      │                │        3           │
  │  ⚠ can be renamed  │      vs        │  ✓ never changes   │
  │  ⚠ 9 bytes × 1bn   │                │  ✓ 4 bytes         │
  └────────────────────┘                └────────────────────┘
        keep it as a normal column            use it for joins
```

```sql
CREATE OR REPLACE TABLE dim_toy AS
SELECT
  row_number() OVER (ORDER BY toy_name) AS toy_key,   -- the sticker
  toy_name,                                           -- the natural key, kept
  toy_category
FROM (SELECT DISTINCT toy_name, toy_category FROM raw_sales);
```

```
toy_key | toy_name    | toy_category
      1 | Kite        | Outdoor
      2 | Puzzle Cube | Puzzles
      3 | Red Robot   | Robots
```

**Keep the natural key as a normal column.** You need it to match against source data, and it's the first thing you check when a join looks wrong.

**One exception worth knowing:** date dimensions use a readable integer key — `20260801` for 1 August 2026. Everyone does this. You can read it at a glance and it sorts correctly.

### Exercise

Build `dim_kid` with a surrogate key. Then notice the problem: Ben appears with two different cities. Decide what `dim_kid` should contain, and defend the choice in a SQL comment.

<details>
<summary><b>Show solution</b></summary>

First, find the problem:

```sql
SELECT kid_name, count(DISTINCT kid_city) AS cities
FROM raw_sales GROUP BY 1 HAVING count(DISTINCT kid_city) > 1;
-- Ben, 2
```

```sql
-- Grain: one row = one kid (current state).
-- Ben appears in two cities. Two possibilities: he moved, or one is a typo.
-- We cannot tell from this data, which is itself the finding.
-- Taking the most recent value is the pragmatic Type 1 choice; if anyone
-- needs "where did Ben live when he bought this", this must become Type 2.
CREATE OR REPLACE TABLE dim_kid AS
SELECT
  row_number() OVER (ORDER BY kid_name) AS kid_key,
  kid_name,
  kid_city
FROM (
  SELECT kid_name, kid_city,
         row_number() OVER (PARTITION BY kid_name ORDER BY sold_at DESC) AS rn
  FROM raw_sales
) WHERE rn = 1;
```

**The real answer in a job is: go ask someone.** "Does Ben have two rows because he moved?" is a business question, not a SQL question, and guessing is how bad models get built.
</details>

## 5. The date dimension

### Explain

Almost every model has one. It's a table with one row per calendar day and a column for every way anyone might want to slice time.

```
   Every fact table points at the same calendar
                    ┌─────────────┐
                    │  dim_date   │
                    │ ─────────── │
   fct_sales  ────▶ │ date_key    │ ◀──── fct_returns
                    │ full_date   │
   fct_stock  ────▶ │ day_name    │ ◀──── fct_shipments
                    │ month_no    │
                    │ quarter     │
                    │ is_weekend  │
                    │ is_holiday  │ ← ✱ not a SQL function. A business fact.
                    │ fiscal_qtr  │ ← ✱ same. Defined once, here.
                    └─────────────┘
```

**Why bother, when SQL has date functions?** Because "is this a public holiday in Ontario?" and "which fiscal quarter is this?" are *not* SQL functions. They're business facts. The date dimension is where they live, defined once, so every report agrees.

```sql
CREATE OR REPLACE TABLE dim_date AS
SELECT
  CAST(strftime(d, '%Y%m%d') AS INTEGER) AS date_key,
  d                                      AS full_date,
  dayname(d)                             AS day_name,
  CAST(strftime(d,'%m') AS INTEGER)      AS month_no,
  dayofweek(d) IN (0,6)                  AS is_weekend
FROM (SELECT DISTINCT CAST(sold_at AS DATE) AS d FROM raw_sales);
```

In real life you generate 30 years of dates up front, not just the days you happen to have sales for.

### Exercise

Build a `dim_date` covering **every** day from 2026-01-01 to 2026-12-31 — not just days with sales. Include `date_key`, `full_date`, `day_name`, `month_no`, `quarter`, `is_weekend`.

<details>
<summary><b>Show solution</b></summary>

```sql
CREATE OR REPLACE TABLE dim_date AS
SELECT
  CAST(strftime(d, '%Y%m%d') AS INTEGER) AS date_key,
  CAST(d AS DATE)                        AS full_date,
  dayname(d)                             AS day_name,
  CAST(strftime(d, '%m') AS INTEGER)     AS month_no,
  CAST(strftime(d, '%Y') AS INTEGER)     AS year_no,
  quarter(d)                             AS quarter_no,
  dayofweek(d) IN (0, 6)                 AS is_weekend
FROM generate_series(DATE '2026-01-01', DATE '2026-12-31', INTERVAL 1 DAY) AS t(d);
```

365 rows. Generating the full year rather than only days with sales is the point: **a report for a quiet week should show zeros, not missing rows.**

In Snowflake the equivalent generator is `GENERATOR(ROWCOUNT => n)` with `DATEADD`.
</details>

## 6. The star schema

### Explain

Put the fact table in the middle. Put the dimensions around it. Draw the joins. It looks like a star.

```
                       ┌──────────┐
                       │ dim_date │
                       └────┬─────┘
                            │
      ┌─────────┐    ┌──────┴────────┐    ┌─────────┐
      │ dim_kid │────│ fct_sale_line │────│ dim_toy │
      └─────────┘    └──────┬────────┘    └─────────┘
                            │
                       ┌────┴─────┐
                       │ dim_shop │
                       └──────────┘
```

```sql
CREATE OR REPLACE TABLE dim_shop AS
SELECT row_number() OVER (ORDER BY shop_name) AS shop_key, shop_name
FROM (SELECT DISTINCT shop_name FROM raw_sales);

CREATE OR REPLACE TABLE fct_sale_line AS
SELECT
  s.receipt_no,                                          -- degenerate dimension
  CAST(strftime(s.sold_at,'%Y%m%d') AS INTEGER) AS date_key,
  k.kid_key, t.toy_key, sh.shop_key,
  s.quantity,
  s.toy_price               AS unit_price,
  s.quantity * s.toy_price  AS line_total
FROM raw_sales s
JOIN dim_kid  k  ON k.kid_name   = s.kid_name
JOIN dim_toy  t  ON t.toy_name   = s.toy_name
JOIN dim_shop sh ON sh.shop_name = s.shop_name;
```

Now every analytical question has the **same shape**: pick the fact table, join the dimensions you need, group by dimension columns, sum fact columns. That predictability is the actual product. Analysts stop asking you how to join things.

**Degenerate dimensions.** `receipt_no` sits in the fact table with no dimension of its own. That's fine and it has a name. It's an identifier you want to group by ("how many toys per receipt?") but there's nothing else to say about a receipt. Don't build a `dim_receipt` with one column in it.

**Star vs snowflake.** If you split `dim_toy` further — a separate `dim_category` that `dim_toy` points to — the diagram grows branches and it's called a *snowflake schema* (no relation to the warehouse; the name is much older). Mostly, don't. It saves trivial space and costs an extra join on every query. Keep dimensions flat and wide.

### Exercise

**(a)** Build `fct_sale_line` joining all four dimensions. Verify it has exactly 6 rows and that `sum(line_total)` matches the raw table.

**(b)** Write the revenue-by-category query against your star, then the same query against `raw_sales`. Compare how each would change if categories got renamed.

<details>
<summary><b>Show solution</b></summary>

**(a)**

```sql
SELECT count(*) AS n, sum(line_total) AS revenue FROM fct_sale_line;
-- 6, 194.46
```

Always compare the fact row count and total against the source. **An `INNER JOIN` to a dimension that's missing a row will silently drop facts**, and that's a bad way to lose money.

**(b)**

```sql
-- star
SELECT t.toy_category, sum(f.line_total) AS revenue, sum(f.quantity) AS units
FROM fct_sale_line f JOIN dim_toy t USING (toy_key)
GROUP BY 1 ORDER BY revenue DESC;

-- raw
SELECT toy_category, sum(quantity * toy_price) AS revenue
FROM raw_sales GROUP BY 1 ORDER BY revenue DESC;
```

Both return:

```
toy_category | revenue | units
Robots       |  104.96 |     4
Puzzles      |   47.50 |     5
Outdoor      |   42.00 |     3
```

The difference is what happens on a rename. In the star, `UPDATE dim_toy SET toy_category='Robotics' WHERE toy_category='Robots'` touches **one row**. Against raw, it touches every fact row that ever mentioned robots — and if the load is append-only, you can't update history at all.
</details>

## 7. Why not one big table

### Explain

Fair question, and it comes up in every design review.

**The case for it:** modern warehouses are columnar. They only read the columns you ask for, so a 200-column table isn't slow if you select 3. Joins cost something. Storage is cheap. For a single dashboard with one team — honestly, you can. Don't build a star schema for one report.

**Where it falls apart:**

```
  ONE BIG TABLE                          STAR SCHEMA
  ─────────────                          ───────────
  Rename a category?                     Update 1 row in dim_toy
  → rewrite 1,000,000,000 rows

  "Which toys sold NOTHING?"             LEFT JOIN from dim_toy
  → impossible. Absence has no row.      → answered instantly

  Price changed last month?              SCD2 rows with valid_from/valid_to
  → table has both numbers, no way
    to know which was right when

  Sales per line, stock per day,         Three fact tables sharing
  returns per item?                      the same dimensions
  → can't flatten without inventing
    rows that mean nothing

  Marketing's "revenue" vs               Shared dimensions =
  finance's "revenue"                    the whole org agrees
  → every meeting starts with an argument
```

**The actual answer:** use a star schema for the **core** layer many people build on. Build **one big flat table on top of it** for a specific dashboard that needs to be fast and simple. Both, in that order.

### Exercise

Using a left join from `dim_toy`, find toys that sold nothing on 2026-08-03. Then explain in one sentence why `raw_sales` alone cannot answer this.

<details>
<summary><b>Show solution</b></summary>

```sql
SELECT t.toy_name
FROM dim_toy t
LEFT JOIN fct_sale_line f
  ON f.toy_key = t.toy_key AND f.date_key = 20260803
WHERE f.toy_key IS NULL;
-- Kite, Puzzle Cube
```

**`raw_sales` can't answer it because absence has no row.** A toy that sold nothing simply doesn't appear. The dimension is the complete list of things that *exist*, so it's the only place a "what didn't happen" question can start.

Note the join condition placement: `date_key = 20260803` must be in the `ON` clause, not the `WHERE`. Put it in `WHERE` and the left join collapses into an inner join and you get zero rows.

This is the strongest single argument for dimensions.
</details>

## 8. Measures

### Explain

```
 ADDITIVE          ── add across everything ──▶  quantity, line_total
 ┌───┬───┬───┐
 │ 2 │ 3 │ 1 │ = 6  ✓ by day, by kid, by toy, any combination
 └───┴───┴───┘

 SEMI-ADDITIVE     ── adds across things, NOT time ──▶  stock, balance
 Mon: 50  Tue: 50   50+50 = 100 shirts? ❌ It's the SAME 50 shirts.
                    Take the LAST value, not the sum.

 NON-ADDITIVE      ── never add these ──▶  prices, ratios, percentages
 $24.99 + $9.50 = $34.49  ← a number that means literally nothing
```

**Rule: store the parts, divide at the end.** Never store the average.

`sum(line_total) / sum(quantity)` — not `avg(unit_price)`. The second treats a 1-unit sale and a 400-unit sale as equally important.

### Exercise

Classify each measure as additive, semi-additive, or non-additive, and say why: `quantity`, `line_total`, `unit_price`, and a hypothetical `stock_on_hand`.

<details>
<summary><b>Show solution</b></summary>

| Measure | Type | Why |
|---|---|---|
| `quantity` | additive | sums across any dimension |
| `line_total` | additive | same |
| `unit_price` | non-additive | summing prices is meaningless; average it, **weighted by quantity** |
| `stock_on_hand` | semi-additive | sums across shops, but not across days — take the latest |

The weighted average matters:

```sql
SELECT sum(line_total) / sum(quantity) AS avg_price_paid FROM fct_sale_line;
```

not `avg(unit_price)`.
</details>

## 9. Slowly changing dimensions

### Explain

The Red Robot cost $24.99 in July and $29.99 in August. Ben lived in Toronto, then moved to Mississauga. What should the dimension say?

This is the **slowly changing dimension** problem — "slowly" because kids move house occasionally, not constantly. Two answers you actually need.

```
 TYPE 1 — OVERWRITE                    TYPE 2 — KEEP BOTH, WITH DATES
 ──────────────────                    ─────────────────────────────
 Ben | Mississauga                     Ben | Toronto     | 2026-01-01 → 2026-08-02 | old
                                       Ben | Mississauga | 2026-08-03 → 9999-12-31 | ✓ current
 History erased.
 His July orders now                   His July orders still say Toronto,
 look like Mississauga.                because that's where he was.

 Use when: it was a typo,              Use when: anyone needs last year's
 or history truly doesn't matter.      report to still produce last year's numbers.
```

Think of it like this: your friend moves house. You don't erase the birthday card you sent them last year — it really did go to the old address. You just start using the new one from now on.

```sql
CREATE OR REPLACE TABLE dim_toy_scd2 (
  toy_key INTEGER, toy_name VARCHAR, toy_category VARCHAR, list_price DECIMAL(10,2),
  valid_from DATE, valid_to DATE, is_current BOOLEAN
);

INSERT INTO dim_toy_scd2 VALUES
 (1,'Kite','Outdoor',14.00, DATE '2026-01-01', DATE '9999-12-31', TRUE),
 (2,'Puzzle Cube','Puzzles',9.50, DATE '2026-01-01', DATE '9999-12-31', TRUE),
 (3,'Red Robot','Robots',24.99, DATE '2026-01-01', DATE '2026-08-02', FALSE),
 (4,'Red Robot','Robots',29.99, DATE '2026-08-03', DATE '9999-12-31', TRUE);
```

Notice: **the Red Robot has two rows and two different surrogate keys.** `toy_key` 3 is the old version, 4 is the new one. `toy_name` stays the same in both — that's the natural key, and it's how you know they're the same toy.

Three columns do the work:
- `valid_from` / `valid_to` — the window this version was true
- `is_current` — a shortcut flag so the common query is easy
- `9999-12-31` as "still true" — an actual date, so `BETWEEN` works without special-casing NULLs

Asking **"what was true then?"**:

```sql
SELECT s.receipt_no, CAST(s.sold_at AS DATE) AS d, t.list_price AS price_then
FROM raw_sales s
JOIN dim_toy_scd2 t
  ON t.toy_name = s.toy_name
 AND CAST(s.sold_at AS DATE) BETWEEN t.valid_from AND t.valid_to
WHERE s.toy_name = 'Red Robot';
```

```
R-001 | 2026-08-01 | 24.99
R-002 | 2026-08-01 | 24.99
R-005 | 2026-08-03 | 29.99
```

A Type 1 dimension would have said $29.99 for all three, and your July revenue report would have been wrong.

**The rule for which type:** does anyone need last year's report to still produce last year's numbers? If yes, Type 2. In finance, regulated industries, and anything audited, the answer is always yes.

> **Tip.** In your fact table, store the surrogate key that was correct at the time. Once `fct_sale_line` holds `toy_key = 3` for that 1 August sale, the price is locked in forever and you never do the `BETWEEN` join again. **That's the real reason surrogate keys exist.**

## 10. The fan-out trap

### Explain

The bug you will meet, guaranteed, probably in your first month.

Suppose `dim_kid` accidentally has Ana twice — a bad merge, a duplicated load, whatever.

```
  FACT (correct)              DIM (has a duplicate)        RESULT
  ┌──────────────┐            ┌────────────┐               ┌──────────────┐
  │ Ana | 49.98  │───┐    ┌──▶│ 1 | Ana    │               │ Ana | 49.98  │
  │ Ana |  9.50  │   ├────┤   │ 1 | Ana ⚠  │  ────────▶    │ Ana | 49.98  │ ⚠
  │ Ben | 24.99  │   │    └──▶└────────────┘               │ Ana |  9.50  │
  └──────────────┘   │                                     │ Ana |  9.50  │ ⚠
                     └── each fact row matched TWICE        │ Ben | 24.99  │
                                                            └──────────────┘
   sum = 194.46                                              sum = 295.94

        💸 REVENUE WENT UP BY JOINING A TABLE THAT CONTAINS NO REVENUE
```

Nothing errored. The query looks perfectly reasonable. The dashboard is just wrong, by 52%.

**How to defend against it:**

1. **Test that every dimension is unique on its key.** One row per key, always.
2. **Watch your row count across joins.** A dimension join should never change the fact row count.
3. **Be suspicious when a total goes up after you add a join.** Joins should never create money.

### Exercise

Deliberately duplicate a row in `dim_toy`, join it to the fact table, and show that revenue inflates. Then write the test that would have caught it.

<details>
<summary><b>Show solution</b></summary>

```sql
CREATE OR REPLACE TABLE dim_toy_dupe AS
SELECT * FROM dim_toy
UNION ALL
SELECT * FROM dim_toy WHERE toy_name = 'Red Robot';

SELECT sum(f.line_total) FROM fct_sale_line f
JOIN dim_toy_dupe t ON t.toy_key = f.toy_key;
-- inflated: Red Robot's rows counted twice
```

The catch:

```sql
SELECT toy_key, count(*) AS n
FROM dim_toy_dupe GROUP BY 1 HAVING count(*) > 1;
```

Run that on **every dimension, every load.** In dbt it's the built-in `unique` test; in plain SQL it's four lines.
</details>

## 11. Tests

### Explain

```
  THE CONVENTION:  a test returns rows  ⟺  the test FAILED
                   and those rows ARE your problem list.
                   Zero rows = healthy. 🟢
```

Four tests catch most of what goes wrong:

```
  1. GRAIN UNIQUENESS      — is one row really one thing?
  2. DIM KEY UNIQUENESS    — will this join fan out?
  3. NO ORPHAN FKs         — does every fact point at a real dimension row?
  4. SANITY RANGES         — negative quantities, future dates, nulls
```

Write these **before** you write the model. It's the step people skip and the one that costs weeks.

### Exercise

Write four tests as SQL, each returning zero rows when healthy: grain uniqueness, dimension key uniqueness, no orphan `toy_key` in the fact table, and no negative quantities.

<details>
<summary><b>Show solution</b></summary>

```sql
-- 1. grain uniqueness on the fact table
SELECT receipt_no, toy_key, count(*)
FROM fct_sale_line GROUP BY 1,2 HAVING count(*) > 1;

-- 2. dimension key uniqueness
SELECT toy_key, count(*) FROM dim_toy GROUP BY 1 HAVING count(*) > 1;

-- 3. no orphan foreign keys
SELECT f.toy_key FROM fct_sale_line f
LEFT JOIN dim_toy t USING (toy_key) WHERE t.toy_key IS NULL;

-- 4. no negative quantities
SELECT * FROM fct_sale_line WHERE quantity <= 0;
```

All four return zero rows when healthy. Wrap each in a `pytest` assertion and you've got the beginnings of a real data quality suite.
</details>

## 12. Layers

### Explain

Real pipelines have floors. Names differ by shop; the shape is always the same.

```
  ┌──────────────────────────────────────────────────────────────┐
  │ RAW  (landing / bronze)                                      │
  │ Exact copy of the source. Ugly column names and all.         │
  │ RULE: never edit. Append only.                               │
  ├──────────────────────────────────────────────────────────────┤
  │ STAGING  (silver / prep)                                     │
  │ Cleaned and typed. One model per source table.               │
  │ RULE: no joins between sources. No business logic.           │
  ├──────────────────────────────────────────────────────────────┤
  │ CORE  (marts / gold / warehouse)                             │
  │ Your star schema. Facts and dimensions.                      │
  │ RULE: business logic lives here, ONCE.                       │
  ├──────────────────────────────────────────────────────────────┤
  │ REPORTING  (presentation)                                    │
  │ Flat wide tables for one dashboard or team.                  │
  │ RULE: cheap, disposable, rebuild freely.                     │
  └──────────────────────────────────────────────────────────────┘
```

- **Why raw is untouchable.** When you find a bug in three months you need to reprocess. If you cleaned on the way in and threw away the original, you can't. Storage is cheaper than re-extracting from a source that may not even have the history anymore.
- **Why staging exists.** It's the only place allowed to know the source calls it `cust_nm_1`. Everything downstream sees `customer_name`. Source changes → you fix one model.
- **Why reporting is disposable.** It's shaped for one audience. When the dashboard changes you rewrite it — fine, because the core beneath it didn't move.

The discipline that matters: **business logic lives in exactly one layer.** If "active customer" is defined in three places, they will drift, and reconciling them is a miserable week.

### Exercise

Given these four requirements, say which layer each belongs in and why:
(a) rename `cust_nm_1` to `customer_name`; (b) define "a VIP kid is one who spent over $100"; (c) keep the raw JSON exactly as the API returned it; (d) a single flat table the marketing dashboard reads.

<details>
<summary><b>Show solution</b></summary>

| Requirement | Layer | Why |
|---|---|---|
| (a) rename `cust_nm_1` | **Staging** | Source-shape knowledge is quarantined here so nothing downstream knows the ugly name |
| (b) "VIP = spent > $100" | **Core** | Business logic, defined once, so marketing and finance can't disagree |
| (c) raw JSON as returned | **Raw** | Never edited; it's your only safety net when you need to reprocess |
| (d) flat marketing table | **Reporting** | Shaped for one audience, disposable, rebuilt when the dashboard changes |

The trap answer is putting (b) in reporting. Do that once per team and you get three definitions of "VIP" that drift apart within a quarter.
</details>

## 13. Snowflake specifics

### Explain

Things that differ from what textbooks assume.

```
  ┌─────────────────────────────────────────────────────────────────┐
  │ PK / FK are NOT ENFORCED                                        │
  │ You can declare them; Snowflake will happily insert duplicates. │
  │ Declare them anyway (optimiser hints + documentation) but       │
  │ YOUR TESTS ARE THE ONLY REAL ENFORCEMENT.                       │
  ├─────────────────────────────────────────────────────────────────┤
  │ NO INDEXES — micro-partitions instead                           │
  │ Table auto-chopped into ~16MB chunks, min/max recorded per      │
  │ column per chunk. Filter on a date → chunks that can't match    │
  │ are skipped entirely. That's "pruning".                         │
  │   [ chunk 1: Jan 1–3 ] [ chunk 2: Jan 4–6 ] [ chunk 3: Jan 7–9 ]│
  │   WHERE d = 'Jan 5'  →  skip 1, read 2, skip 3                  │
  ├─────────────────────────────────────────────────────────────────┤
  │ CLUSTERING KEYS — sparingly                                     │
  │ Only on very large tables (hundreds of GB) where insert order   │
  │ ≠ filter order. Costs credits continuously. Measure first.      │
  ├─────────────────────────────────────────────────────────────────┤
  │ WIDE DIMENSIONS ARE FINE                                        │
  │ Columnar storage: a 100-column dim costs nothing if you select  │
  │ 5. This is the technical reason to prefer flat over snowflaked. │
  ├─────────────────────────────────────────────────────────────────┤
  │ STREAMS + TASKS = your SCD2 machinery                           │
  │ Stream tracks what changed since you last looked; Task runs on  │
  │ a schedule. Together: incremental Type 2 without full reloads.  │
  ├─────────────────────────────────────────────────────────────────┤
  │ ZERO-COPY CLONE                                                 │
  │ CREATE TABLE dev_fct CLONE prod_fct;                            │
  │ Instant, no storage cost until you change something. Test model │
  │ changes against real volumes. Wildly underused.                 │
  └─────────────────────────────────────────────────────────────────┘
```

> **Trap.** Time Travel is not history. It lets you query a table as it was up to 90 days ago, for recovering from mistakes. It is *not* a substitute for Type 2 dimensions — it tracks **what your table said**, not **what was true in the business**. Confusing these two is a common interview trip-up.

### Exercise

A colleague says: *"We don't need SCD Type 2 — Snowflake has Time Travel, we can just query the dimension as of any past date."* Write the two-sentence rebuttal you'd give in a design review.

<details>
<summary><b>Show solution</b></summary>

> Time Travel tells you what the *table* contained at a past moment, which is only the same as business history if the table was always correct and always loaded on time — a late load, a backfill, or a bug means the table said the wrong thing on that date. Type 2 records what was *true in the business* between two dates regardless of when we loaded it, and it only goes back 90 days at most, so it can't answer "what did this customer's segment look like in 2024" at all.

Bonus points for adding: Time Travel is for **recovery** (you dropped a table, you ran a bad `UPDATE`); SCD2 is for **reporting**. Different jobs.
</details>

## 14. Capstone: returns

### Explain

**The recipe.** When someone hands you a new source and says "model this," do these six steps in order. (Kimball's four, plus two that matter in practice.)

```
  1. PICK THE BUSINESS PROCESS   "A toy is sold." Not a table — an EVENT.
             ↓                    One process, one fact table.
  2. DECLARE THE GRAIN OUT LOUD  "One row is one product on one receipt."
             ↓                    Write it in a comment at the top. ★
  3. LIST THE DIMENSIONS         Everything after "by" or "for".
             ↓
  4. LIST THE FACTS              Numbers that make sense AT THAT GRAIN.
             ↓
  5. DECIDE WHAT CHANGES         Type 1 or Type 2, per dimension.
             ↓                    Deciding later means a backfill.
  6. WRITE THE TESTS FIRST       Grain, dim keys, orphans, row counts. ★

  ★ = the two people skip, and the two that cost weeks.
```

**The mistakes list**, in rough order of how much they cost:

1. **Mixing grains in one table.** Every aggregate wrong, forever.
2. **Modelling the source system instead of the business.** If your warehouse mirrors the app's tables, you built a slow read replica.
3. **Putting descriptions in the fact table.** Renaming a category becomes a billion-row update.
4. **Storing averages.** Store `sum_revenue` and `count_orders`. An average of averages is not the average.
5. **No date dimension.** You'll regret it the first time someone asks for fiscal quarters.
6. **Deciding SCD type after loading history.** The history you needed is already gone. When in doubt and the dimension is small, go Type 2.
7. **Trusting declared keys in Snowflake.** Documentation, not constraints. Test them.
8. **Building a star for one dashboard.** Modelling is a cost. Spend it where many people benefit.

Add **returns** to the shop: a kid can bring a toy back. Design it.

- Declare the grain.
- Defend the choice in a SQL comment.

<summary><b>Show solution</b></summary>

```sql
-- DECISION: separate fact table, not negative rows in fct_sale_line.
--
-- Grain: one row = one toy returned on one return slip.
--
-- Why separate:
--   * Different event, different date. A toy sold on the 1st and returned
--     on the 10th belongs to two different days. Negative rows would force
--     one date onto both, and any daily revenue figure would be wrong.
--   * Different attributes. Returns have a reason code; sales don't.
--   * Different grain risk. A return can be partial, and quantities returned
--     don't have to match quantities sold.
--   * Sales stay immutable. What we sold on the 1st never changes.
--
-- Negative rows would be acceptable only if returns were always same-day
-- and carried no extra attributes — rare in practice.

CREATE OR REPLACE TABLE fct_return_line (
  return_no    VARCHAR,
  receipt_no   VARCHAR,    -- links back to the original sale
  date_key     INTEGER,    -- date of the RETURN
  kid_key      INTEGER,
  toy_key      INTEGER,
  shop_key     INTEGER,
  quantity     INTEGER,    -- positive; the sign lives in the semantics
  refund_total DECIMAL(10,2),
  reason_code  VARCHAR
);

INSERT INTO fct_return_line VALUES
 ('RT-01','R-001', 20260805, 1, 3, 2, 1, 24.99, 'FAULTY');
```

Net revenue:

```sql
WITH sales AS (
  SELECT date_key, toy_key, sum(line_total) AS gross
  FROM fct_sale_line GROUP BY 1,2
),
refunds AS (
  SELECT date_key, toy_key, sum(refund_total) AS refunded
  FROM fct_return_line GROUP BY 1,2
)
SELECT
  coalesce(s.toy_key, r.toy_key) AS toy_key,
  coalesce(sum(s.gross), 0)      AS gross_revenue,
  coalesce(sum(r.refunded), 0)   AS refunds,
  coalesce(sum(s.gross), 0) - coalesce(sum(r.refunded), 0) AS net_revenue
FROM sales s
FULL OUTER JOIN refunds r ON s.toy_key = r.toy_key AND s.date_key = r.date_key
GROUP BY 1 ORDER BY net_revenue DESC;
```

**`FULL OUTER JOIN` matters here:** a day with returns but no sales still needs a row, otherwise refunds silently vanish from your totals.

Two fact tables sharing the same dimensions is called a **fact constellation**, and it's the normal shape of a real warehouse:

```
                 dim_date
                /        \
   fct_sale_line          fct_return_line
       |     \            /      |
   dim_kid   dim_toy   dim_shop  (shared — this is the point)
```
</details>

4. **`count(*)` before and after every join.** Fact row counts should not move.
