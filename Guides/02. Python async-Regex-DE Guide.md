# Part 1 — Asynchronous Python

## 1. Why async exists

### Explain

Imagine loading 200 files from an API into Snowflake. Each call takes 1 second — but almost none of that second is your computer *doing work*. It's your computer **waiting** for the network.

```
  NORMAL PYTHON                        ASYNC PYTHON
  ─────────────                        ────────────
  call 1: [====wait 1s====] done       call 1: [====wait====] ┐
  call 2:                  [==wait==]  call 2: [====wait====] │ all
  call 3:                           [  call 3: [====wait====] │ at
  ...                                  ...                    │ once
  ═══ 200 seconds ═══                  ═══ ~1-2 seconds ═══   ┘
  CPU idle the whole time
```

**In one sentence: async lets one program do something useful while it waits, instead of standing still.**

The waiter analogy is the one that sticks:

```
  BAD WAITER                          GOOD WAITER
  takes order → walks to kitchen →    takes order → hands it to kitchen →
  STANDS THERE WATCHING THE CHEF →    immediately goes to next table →
  brings food → next table            comes back when food is ready

  Same one waiter. Far more tables served.
  The waiter never cooks faster — they just stop standing around.
```

> **Trap.** Critical limit: async only helps with *waiting*. It does **not** make computation faster. If your bottleneck is a heavy pandas transform or a big sort, async does nothing for you (see [1.11](#111--when-not-to-use-async)).

For a data engineer, "waiting" means: API calls, database queries, reading/writing cloud storage, message queues. Which is most of what a pipeline does.

### Exercise

Write `fetch_table(name, seconds)` that sleeps and returns `{"table": name, "rows": 100}`. Call it for five tables sequentially with a `for` loop, then with `gather`. Print elapsed time for each and confirm the difference.

### Solution

```python
import asyncio
import time

async def fetch_table(name: str, seconds: float) -> dict:
    await asyncio.sleep(seconds)
    return {"table": name, "rows": 100}

async def main() -> None:
    tables = ["orders", "customers", "payments", "refunds", "invoices"]

    start = time.perf_counter()
    sequential = []
    for t in tables:
        sequential.append(await fetch_table(t, 1))
    print(f"sequential: {time.perf_counter() - start:.2f}s")

    start = time.perf_counter()
    concurrent = await asyncio.gather(*(fetch_table(t, 1) for t in tables))
    print(f"gather:     {time.perf_counter() - start:.2f}s")

    assert sequential == concurrent

asyncio.run(main())
```

Roughly **5.00s vs 1.00s**.

> **Trap.** The `for` loop with `await` inside is **fully sequential** — each `await` finishes before the next iteration starts. That loop is the most common accidental way to write slow async code.

## 2. The three words you need

### Explain

**Coroutine** — a function defined with `async def`. Calling it does **not** run it. It hands you back an object that says "I'm ready to run when someone runs me."

**await** — "start this, and let other work happen until it comes back." Only usable inside an `async def`.

**Event loop** — the manager. It holds all your paused tasks and wakes each one the moment its wait is over. `asyncio.run()` starts it.

```
                        THE EVENT LOOP
       ┌───────────────────────────────────────────────┐
       │   ┌────────┐   ┌────────┐   ┌────────┐        │
       │   │ task A │   │ task B │   │ task C │        │
       │   │ paused │   │ RUNNING│   │ paused │        │
       │   │ at     │   │        │   │ at     │        │
       │   │ await  │   │        │   │ await  │        │
       │   └────────┘   └────────┘   └────────┘        │
       │        ▲                          │           │
       │        └──── wakes whichever ─────┘           │
       │              finishes waiting first           │
       └───────────────────────────────────────────────┘

   ★ A coroutine runs from its start to its FIRST await
     without interruption. Control only changes hands at an await.
```

The single most common beginner mistake:

```python
async def get_data():
    await asyncio.sleep(1)
    return "rows"

result = get_data()          # ❌ WRONG — result is a coroutine object
result = await get_data()    # ✅ RIGHT — inside an async function
```

If you ever print something and see `<coroutine object get_data at 0x7f...>`, **you forgot an `await`**. That's the whole bug, every time.

### Exercise

**Predict the output order before you run it.** Then run it. If your prediction was wrong, work out why — this exercise is worth more than the rest of Part 1 combined.

```python
import asyncio

async def a():
    print("a start")
    await asyncio.sleep(0)
    print("a end")

async def b():
    print("b start")
    await asyncio.sleep(0.1)
    print("b end")

async def main():
    print("main start")
    await asyncio.gather(a(), b())
    print("main end")

asyncio.run(main())
```

### Solution

```
main start
a start
b start
a end
b end
main end
```

Why:

1. `main` prints, then hits `gather`, which schedules both coroutines.
2. `a` runs **until its first `await`**. Prints "a start", hits `sleep(0)`, gives up control.
3. `b` runs. Prints "b start", hits `sleep(0.1)`, gives up control.
4. `a`'s sleep was 0 seconds, so it's ready immediately. Prints "a end".
5. 0.1s later `b` wakes. Prints "b end".
6. Both done, `gather` returns, "main end".

**The point:** a coroutine runs from its start to its first `await` without interruption. Control only ever changes hands at an `await`. If you understand this, you understand the event loop.

> **Tip.** `await asyncio.sleep(0)` is a useful idiom on its own — it means "let other tasks have a turn right now."

## 3. Running many at once

### Explain

Two tools. Learn both; they're used in different situations.

```
  asyncio.gather(...)                    asyncio.TaskGroup()   (3.11+)
  ─────────────────                      ───────────────────
  results = await asyncio.gather(        async with asyncio.TaskGroup() as tg:
      fetch("orders",   1),                  o = tg.create_task(fetch("orders", 1))
      fetch("customers",2),                  c = tg.create_task(fetch("cust",   2))
      fetch("payments", 1),              # everything guaranteed finished here
  )                                      print(o.result(), c.result())

  ✓ results come back as a LIST          ✓ safer on failure (see 1.5)
  ✓ IN THE ORDER YOU PASSED THEM,        ✓ nothing can leak out still running
    not the order they finished          ✗ more typing
  ✓ quick scripts

  Takes 2 seconds, not 4 — as slow as the SLOWEST, not the SUM.
```

Results coming back **in input order** matters more than people expect: it means you can safely `zip` results back against your input list.

For a list you built dynamically, use `*`:

```python
tables = ["orders", "customers", "payments", "refunds"]
results = await asyncio.gather(*(fetch_table(t, 1) for t in tables))
```

**Rule of thumb:** `gather` for quick scripts and when you want results as a list. `TaskGroup` for anything going to production. On Python 3.11+, `TaskGroup` should become your default.

### Exercise

Take your `gather` version from Exercise 1.1 and replace `asyncio.sleep` with `time.sleep`. Measure it. Then explain in **one sentence** why it got slower.

### Solution

```python
import asyncio
import time

async def fetch_table_blocking(name: str, seconds: float) -> dict:
    time.sleep(seconds)          # ← blocking
    return {"table": name, "rows": 100}

async def main() -> None:
    start = time.perf_counter()
    await asyncio.gather(*(fetch_table_blocking(t, 1) for t in ["a","b","c","d","e"]))
    print(f"{time.perf_counter() - start:.2f}s")

asyncio.run(main())
```

About **5 seconds**.

**One sentence:** `time.sleep` blocks the single thread the event loop runs on, so no other task can make progress while it sleeps, and the tasks run one after another exactly as if there were no async at all.

That's the whole of the next section.

## 4. The blocking trap

### Explain

This is the mistake that makes people say "I tried async and it didn't help."

```
  ONE THREAD, shared by every task
  ════════════════════════════════════════════════════════

  await asyncio.sleep(1)        time.sleep(1)
  ┌──────────────────────┐      ┌──────────────────────┐
  │ task A steps aside   │      │ task A FREEZES       │
  │ task B runs  ✓       │      │ task B frozen  ✗     │
  │ task C runs  ✓       │      │ task C frozen  ✗     │
  │ loop keeps spinning  │      │ ENTIRE PROGRAM STOPS │
  └──────────────────────┘      └──────────────────────┘
```

Anything that blocks does this, and most libraries you already use are blocking:

| Blocking (freezes the loop) | Async-safe |
|---|---|
| `time.sleep()` | `await asyncio.sleep()` |
| `requests.get()` | `await httpx.AsyncClient().get()` |
| `open()` / `f.read()` | `await aiofiles.open()` |
| `psycopg2`, `snowflake-connector-python` | `asyncpg`, or the escape hatch below |
| `pd.read_csv()` on a huge file | the escape hatch below |

**The escape hatch:** when you must call blocking code, push it to a separate thread so the loop keeps running.

```python
# Modern and simple (Python 3.9+)
rows = await asyncio.to_thread(snowflake_cursor.execute, "SELECT * FROM orders")

# The older form you'll see in existing codebases
loop = asyncio.get_running_loop()
rows = await loop.run_in_executor(None, blocking_function, arg1, arg2)
```

`asyncio.to_thread` is the one to reach for. Remember it — **Snowflake's Python connector is synchronous**, so you will need this.

🔍 **How to spot the bug:** if your "async" code takes exactly as long as the sequential version, you have a blocking call hiding in there. That symptom has one cause.

### Exercise

You've inherited this function. It's "async" but the pipeline is no faster than before. Fix it two ways: once by swapping the library call, once with the escape hatch (pretend you cannot change the library).

```python
import time, requests

async def fetch_and_stage(url: str) -> dict:
    resp = requests.get(url, timeout=30)
    time.sleep(0.5)              # "polite delay" someone added
    return resp.json()
```

### Solution

**Fix 1 — swap for async-native libraries:**

```python
import asyncio
import httpx

async def fetch_and_stage(client: httpx.AsyncClient, url: str) -> dict:
    resp = await client.get(url, timeout=30)
    await asyncio.sleep(0.5)
    return resp.json()

async def main():
    async with httpx.AsyncClient() as client:
        results = await asyncio.gather(*(fetch_and_stage(client, u) for u in urls))
```

Note the client is created **once** and shared. Creating an `AsyncClient` per request throws away connection pooling and is its own performance bug.

**Fix 2 — escape hatch, library unchanged:**

```python
import asyncio
import requests

async def fetch_and_stage(url: str) -> dict:
    resp = await asyncio.to_thread(requests.get, url, timeout=30)
    await asyncio.sleep(0.5)     # this one has no excuse — always fix it
    return resp.json()
```

`to_thread` moves the blocking call onto a worker thread so the event loop stays free. Threads *do* release the GIL while waiting on I/O, which is why this works.

The `time.sleep` has no excuse either way — a "polite delay" belongs in a [Semaphore](#18--semaphores--not-overwhelming-the-thing-you-call) or a rate limiter, not a blocking sleep.

## 5. When things fail

### Explain

Pipelines fail constantly. This section is the difference between a script and a job.

```
  gather(...)  default                  gather(..., return_exceptions=True)
  ────────────────────                  ──────────────────────────────────
  a ✓   b ✗   c ✓                       a ✓   b ✗   c ✓
       ↓                                     ↓
  raises immediately.                   ['a done', ValueError(...), 'c done']
  YOU LOSE a AND c.                     Load the 47 that worked,
                                        log the 3 that didn't.

  TaskGroup
  ─────────
  a ✓   b ✗   c (still running)
       ↓
  b's failure CANCELS c,
  then raises an ExceptionGroup
  containing everything.
```

```python
results = await asyncio.gather(
    fetch("a"), broken_fetch("b"), fetch("c"),
    return_exceptions=True,
)
good = [r for r in results if not isinstance(r, Exception)]
bad  = [r for r in results if isinstance(r, Exception)]
print(f"loaded {len(good)} tables, {len(bad)} failed")
```

Pair results back to inputs by position, since order is guaranteed:

```python
for table, result in zip(tables, results):
    if isinstance(result, Exception):
        logger.error("table %s failed: %s", table, result)
```

`TaskGroup` failure handling uses `except*` (note the star) to catch from an `ExceptionGroup`:

```python
try:
    async with asyncio.TaskGroup() as tg:
        for t in tables:
            tg.create_task(load_table(t))
except* ValueError as eg:
    print(f"{len(eg.exceptions)} tables had bad data")
```

**Choosing between them:**
- `gather(return_exceptions=True)` when **partial success is useful** (most ingestion work).
- `TaskGroup` when **partial success is dangerous** (a set of writes that must land together).

### Exercise

Write `load_file(name)` that fails with `ValueError` if the name contains `"corrupt"`, otherwise succeeds after 0.2s. Run it over `["a", "corrupt_b", "c", "corrupt_d", "e"]`:

**(a)** with `gather(..., return_exceptions=True)` — print `"loaded 3 files, 2 failed"` and log which ones failed.
**(b)** with `TaskGroup` and `except*` — and note what happens to the files that hadn't started yet.

### Solution

**(a)**

```python
import asyncio
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
logger = logging.getLogger(__name__)

async def load_file(name: str) -> str:
    await asyncio.sleep(0.2)
    if "corrupt" in name:
        raise ValueError(f"unreadable file: {name}")
    return f"{name} loaded"

async def main() -> None:
    files = ["a", "corrupt_b", "c", "corrupt_d", "e"]
    results = await asyncio.gather(
        *(load_file(f) for f in files),
        return_exceptions=True,
    )

    good, bad = [], []
    for name, result in zip(files, results):
        if isinstance(result, Exception):
            bad.append(name)
            logger.warning("failed: %s (%s)", name, result)
        else:
            good.append(name)

    print(f"loaded {len(good)} files, {len(bad)} failed")
    print(f"failures: {bad}")

asyncio.run(main())
```

`zip(files, results)` works because `gather` guarantees result order matches input order.

**(b)**

```python
import asyncio

async def main() -> None:
    files = ["a", "corrupt_b", "c", "corrupt_d", "e"]
    tasks = {}
    try:
        async with asyncio.TaskGroup() as tg:
            for f in files:
                tasks[f] = tg.create_task(load_file(f))
    except* ValueError as eg:
        print(f"{len(eg.exceptions)} files failed")
        for exc in eg.exceptions:
            print(f"  {exc}")

    for name, task in tasks.items():
        state = "cancelled" if task.cancelled() else ("failed" if task.exception() else "ok")
        print(f"{name}: {state}")

asyncio.run(main())
```

**What happens to the unstarted ones:** because all five sleep the same 0.2s, they all reach the failure point together and both corrupt files raise. **If the delays differed**, the first failure would cancel every sibling still in flight, and you'd see `cancelled` for tasks that had done nothing wrong.

That's the essential difference: `gather(return_exceptions=True)` lets everything finish; `TaskGroup` stops the whole batch at the first failure.

## 6. Timeouts and cancellation

### Explain

A hung API call with no timeout hangs your pipeline **forever**. Airflow shows the task as running at 3am and nobody knows why.

```
  async with asyncio.timeout(5):
  ┌─────────────────────────────────────────────┐
  │  await step_one()      ← covered            │
  │  await step_two()      ← covered            │
  │  await step_three()    ← covered            │
  └─────────────────────────────────────────────┘
       ⏱ 5s total for the WHOLE block
       ↓ exceeded?
   TimeoutError raised INSIDE, task cancelled, your except runs
```

```python
try:
    async with asyncio.timeout(5):
        data = await slow_api_call()
except TimeoutError:
    logger.warning("api timed out after 5s, using cached data")
    data = cached
```

Older form, still everywhere: `await asyncio.wait_for(slow_api_call(), timeout=5)`.

**Cleanup when cancelled.** When a task is cancelled, Python raises `CancelledError` *inside* it. Use `finally` to release resources:

```python
async def load_with_cleanup(conn):
    try:
        await conn.execute("BEGIN")
        await do_work(conn)
        await conn.execute("COMMIT")
    finally:
        await conn.close()      # runs even on cancellation
```

> **Trap.** Do not swallow `CancelledError`. If you catch it, re-raise it. Catching it silently produces tasks that refuse to die and shutdowns that hang.

```python
except asyncio.CancelledError:
    logger.info("cancelled, cleaning up")
    raise            # ← this line is not optional
```

### Exercise

Write `fetch_with_timeout(seconds)` using `asyncio.timeout(1)`. Call it with `0.5` and with `2.0`. Handle the timeout and return `"fallback"` instead of crashing.

### Solution

```python
import asyncio

async def slow_call(seconds: float) -> str:
    await asyncio.sleep(seconds)
    return "real data"

async def fetch_with_timeout(seconds: float) -> str:
    try:
        async with asyncio.timeout(1):
            return await slow_call(seconds)
    except TimeoutError:
        print(f"timed out after 1s (call needed {seconds}s)")
        return "fallback"

async def main() -> None:
    print(await fetch_with_timeout(0.5))   # real data
    print(await fetch_with_timeout(2.0))   # fallback

asyncio.run(main())
```

> **Tip.** `asyncio.TimeoutError` became an alias for the builtin `TimeoutError` in Python 3.11, so either name works.

## 7. Retry with backoff

### Explain

Networks fail. The correct response is to try again — but **not immediately** and **not forever**.

```
  NO BACKOFF                    EXPONENTIAL BACKOFF          + JITTER
  ──────────                    ───────────────────          ────────
  fail retry retry retry        fail  ─1s─  ─2s─  ─4s─  ─8s─
  ████████████████████                 ▌     ▌      ▌       ▌
  hammering a struggling        gives the service room       spread randomly
  service makes it worse        to recover                   so 200 workers
                                                             don't all retry
                                                             at the same instant
```

**Jitter is not decoration.** Without it, 200 workers that failed simultaneously all retry at exactly t+1s, then all at t+3s. Each retry wave is as large as the original load, so the struggling service gets a synchronised spike right when it's trying to recover. That's a **thundering herd**. Jitter smears each wave into a trickle.

> **Trap.** Only retry what's retryable. A 503 is worth retrying. A 401 or a schema mismatch will fail identically five times while wasting fifteen seconds.

### Exercise

**(a)** Write `flaky_api()` that fails the first two times it's called and succeeds on the third. Wrap it in a retry helper: up to 5 attempts, waiting 1s, 2s, 4s, 8s. Print each attempt.

**(b)** Add jitter, then write one sentence explaining why jitter matters when 200 workers all fail at the same moment.

### Solution

**(a)**

```python
import asyncio

call_count = 0

async def flaky_api() -> str:
    global call_count
    call_count += 1
    await asyncio.sleep(0.05)
    if call_count < 3:
        raise ConnectionError(f"failed on call {call_count}")
    return "success"

async def with_retry(fn, attempts: int = 5, base_delay: float = 1.0):
    for attempt in range(1, attempts + 1):
        try:
            return await fn()
        except ConnectionError as exc:
            if attempt == attempts:
                raise
            delay = base_delay * (2 ** (attempt - 1))
            print(f"attempt {attempt} failed ({exc}), retrying in {delay}s")
            await asyncio.sleep(delay)

print(asyncio.run(with_retry(flaky_api)))
```

Attempt 1 fails, waits 1s; attempt 2 fails, waits 2s; attempt 3 succeeds.

**(b)** One line changes:

```python
delay = base_delay * (2 ** (attempt - 1)) + random.uniform(0, base_delay)
```

**Why it matters:** if 200 workers hit the same outage at the same instant, without jitter all 200 retry at exactly t+1s, then all 200 at t+3s — each retry wave is as large as the original load, so the struggling service gets hit by a synchronised spike right when it's trying to recover.

## 8. Semaphores

### Explain

Firing 5,000 concurrent requests at an API gets you rate-limited, IP-blocked, or takes down an internal service. You need a cap.

A `Semaphore` is a **bouncer holding a fixed number of tickets**. Take one to enter, give it back on the way out.

```
      5,000 tasks created                Semaphore(10)
   ┌─────────────────────────┐        ┌──────────────────┐
   │ ● ● ● ● ● ● ● ● ● ● ●   │        │ 🎟🎟🎟🎟🎟🎟🎟🎟🎟🎟 │
   │ ● ● ● ● ● ● ● ● ● ● ●   │ ─────▶ │  10 tickets      │ ─────▶ API
   │ ● ● ● ... 5000 total    │        │  only 10 inside  │
   └─────────────────────────┘        └──────────────────┘
        all exist                       only 10 RUNNING
        the rest wait politely at the door
```

```python
async def fetch_limited(sem: asyncio.Semaphore, url: str):
    async with sem:                  # wait here if all tickets are taken
        return await fetch(url)

async def main():
    sem = asyncio.Semaphore(10)
    urls = [f"https://api.example.com/page/{i}" for i in range(5000)]
    results = await asyncio.gather(
        *(fetch_limited(sem, u) for u in urls),
        return_exceptions=True,
    )
```

**Picking the number:** start at 10. If the API publishes a rate limit, stay under it. Higher is not always faster — past a point you just build a queue on the server and latency gets worse for everyone. This is a number you tune by **measuring**, not guessing.

### Exercise

Write `fetch(i)` that sleeps 0.1s. Run it for 100 values with a `Semaphore(5)`. Track and print the **peak** number running at once. It should be exactly 5.

### Solution

```python
import asyncio

active = 0
peak = 0

async def fetch(sem: asyncio.Semaphore, i: int) -> int:
    global active, peak
    async with sem:
        active += 1
        peak = max(peak, active)
        await asyncio.sleep(0.1)
        active -= 1
        return i

async def main() -> None:
    sem = asyncio.Semaphore(5)
    await asyncio.gather(*(fetch(sem, i) for i in range(100)))
    print(f"peak concurrency: {peak}")

asyncio.run(main())
```

Prints exactly **5**. Without the semaphore it would print 100.

> **Tip.** Note this counter is only safe because there's **no `await` between reading and writing `active`** — a coroutine can't be interrupted except at an `await`, so those lines are effectively atomic. That's a genuinely useful property of async over threads, where you'd need a lock.

## 9. Queues

### Explain

The shape of a real streaming pipeline: one thing reads, several things process, and the reader doesn't get miles ahead of the writers.

```
   PRODUCER            QUEUE (maxsize=100)              WORKERS
  ┌─────────┐      ┌───────────────────────┐        ┌──────────┐
  │ reads   │ ───▶ │ ▣ ▣ ▣ ▣ ▣ ▣ ▣ ▣ ▣ ▣  │ ─────▶ │ worker 1 │
  │ 50 GB   │      │                       │   ├──▶ │ worker 2 │
  │ source  │      │ FULL? producer PAUSES │   └──▶ │ worker 3 │
  └─────────┘      └───────────────────────┘        └──────────┘
                      ▲                                  ▲
                      │                                  │
              BACKPRESSURE:                     POISON PILLS:
       memory can never exceed 100 rows       one `None` per worker
       no matter how big the source           tells each one to stop
```

```python
async def producer(queue: asyncio.Queue, n_workers: int):
    for record in read_source():
        await queue.put(record)
    for _ in range(n_workers):
        await queue.put(None)          # one poison pill per worker

async def worker(queue: asyncio.Queue, name: str):
    while True:
        record = await queue.get()
        if record is None:             # my signal to stop
            queue.task_done()
            break
        await transform_and_write(record)
        queue.task_done()

async def main():
    n = 5
    queue = asyncio.Queue(maxsize=100)     # ← backpressure
    await asyncio.gather(
        producer(queue, n),
        *(worker(queue, f"w{i}") for i in range(n)),
    )
```

**`maxsize` is the whole point.** Without it, a fast producer reading a 50 GB file pulls the whole thing into memory while slow workers fall behind. This one argument prevents a very common out-of-memory failure.

### Exercise

Build the producer/consumer with a real `asyncio.Queue`, 20 records and 3 workers. Print which worker handled which record. Then set `maxsize=2` and describe what changes.

### Solution

```python
import asyncio

async def producer(queue: asyncio.Queue, n_records: int, n_workers: int) -> None:
    for i in range(n_records):
        await queue.put({"id": i})
        print(f"produced {i}")
    for _ in range(n_workers):
        await queue.put(None)

async def worker(queue: asyncio.Queue, name: str) -> None:
    while True:
        record = await queue.get()
        if record is None:
            queue.task_done()
            print(f"{name} stopping")
            break
        await asyncio.sleep(0.05)
        print(f"{name} handled record {record['id']}")
        queue.task_done()

async def main() -> None:
    n_workers = 3
    queue = asyncio.Queue(maxsize=100)
    await asyncio.gather(
        producer(queue, 20, n_workers),
        *(worker(queue, f"w{i}") for i in range(n_workers)),
    )

asyncio.run(main())
```

**With `maxsize=2`:** the producer prints "produced 0", "produced 1", then **stops and waits**. Production and consumption interleave instead of the producer racing ahead.

That's backpressure — the queue can never hold more than 2 items, so **memory stays bounded no matter how large the source is.**

## 10. Async generators

### Explain

An async generator produces values **over time** instead of all at once. Perfect for paginated APIs, where you don't know the page count up front and don't want all pages in memory.

```
   fetch_all_pages()
   ┌────────────────────────────────────────────────────┐
   │ page 1 → yield → [consumer writes it] → resume     │
   │ page 2 → yield → [consumer writes it] → resume     │
   │ page 3 → yield → ...                               │
   │ empty  → return                                    │
   └────────────────────────────────────────────────────┘
       MEMORY:  ▓ one page      not  ▓▓▓▓▓▓▓▓▓▓▓▓▓ all pages

   Note `async for`, not `for`.
```

```python
async def fetch_all_pages(client, url: str):
    page = 1
    while True:
        response = await client.get(url, params={"page": page})
        data = response.json()
        if not data["results"]:
            return
        yield data["results"]          # hand back one page, then pause
        page += 1

async def main():
    async with httpx.AsyncClient() as client:
        async for batch in fetch_all_pages(client, "https://api.example.com/orders"):
            await write_to_warehouse(batch)
```

Memory stays flat whether there are 3 pages or 30,000, because only one page exists at a time.

### Exercise

Write an async generator `paginate(total_pages)` that yields a list of 3 fake rows per page with a 0.05s delay. Consume it with `async for` and count total rows **without ever holding more than one page in memory**.

### Solution

```python
import asyncio

async def paginate(total_pages: int):
    for page in range(total_pages):
        await asyncio.sleep(0.05)
        yield [{"id": f"{page}-{i}"} for i in range(3)]

async def main() -> None:
    total = 0
    async for batch in paginate(10):
        total += len(batch)
        print(f"got {len(batch)} rows, running total {total}")
    print(f"final: {total}")

asyncio.run(main())
```

30 rows total. Only one page (3 rows) is ever in memory.

The tell that you got it right: you never build a list of all pages. If you wrote `pages = [p async for p in paginate(10)]` you defeated the entire point.

## 11. When not to use async

### Explain

Worth knowing cold — using the wrong one is a classic interview question and a classic production mistake.

Python has a **GIL** (Global Interpreter Lock): only one thread runs Python bytecode at a time in a single process.

```
   YOUR BOTTLENECK              USE                    WHY
  ─────────────────────────────────────────────────────────────────────────
   Network / API / DB /   ──▶  asyncio          Thousands of concurrent
   disk waits                                   waits, one thread, cheap
  ─────────────────────────────────────────────────────────────────────────
   Same, but the library  ──▶  threads          Threads release the GIL
   is blocking                 (to_thread)      during I/O waits
  ─────────────────────────────────────────────────────────────────────────
   Heavy computation —    ──▶  multiprocessing  Separate processes,
   parsing, math, big                           separate GILs,
   transforms                                   real parallelism
  ─────────────────────────────────────────────────────────────────────────
   Genuinely huge data    ──▶  Spark /          Don't hand-roll
                               Snowflake /      distribution in Python
                               DuckDB
```

Said plainly: **asyncio for waiting, multiprocessing for thinking.**

500 APIs to call → async. 500 large XML files to parse → multiprocessing. Both → async for the fetch, hand the parsing to a process pool.

The honest framing: **async is for the orchestration layer of a pipeline. The actual heavy transform belongs in the warehouse.**

### Exercise

For each, say which tool you'd reach for and why in one line:

(a) download 3,000 small JSON files from S3;
(b) parse those 3,000 files into pandas and compute a rolling median per group;
(c) run 40 Snowflake queries and collect the results;
(d) join two 500 GB tables.

### Solution

| | Tool | Why |
|---|---|---|
| (a) download 3,000 JSONs | **asyncio** | Pure waiting on the network — thousands of concurrent waits, one thread |
| (b) parse + rolling median | **multiprocessing** | CPU-bound; the GIL means threads won't help and async does nothing |
| (c) 40 Snowflake queries | **asyncio + `to_thread`** | It's waiting, but the connector is synchronous, so the escape hatch |
| (d) join two 500 GB tables | **the warehouse** | Don't hand-roll distribution in Python. Push it down to Snowflake/Spark |

The pattern to notice in (a)+(b): a real job is often **async for the fetch, then a process pool for the parse**. Those are different tools for different halves of the same pipeline, and combining them is normal.

## 12. Capstone: an ingestion job

### Explain

Everything so far, layered. The layering is the lesson:

```
   ┌─────────────────────────────────────────────────────┐
   │ SEMAPHORE  (cap concurrency at 8)                   │
   │  ┌──────────────────────────────────────────────┐   │
   │  │ RETRY  (up to 3 attempts, exponential+jitter)│   │
   │  │  ┌────────────────────────────────────────┐  │   │
   │  │  │ TIMEOUT  (2s per attempt)              │  │   │
   │  │  │  ┌──────────────────────────────────┐  │  │   │
   │  │  │  │ the actual call                  │  │  │   │
   │  │  │  └──────────────────────────────────┘  │  │   │
   │  │  └────────────────────────────────────────┘  │   │
   │  └──────────────────────────────────────────────┘   │
   └─────────────────────────────────────────────────────┘

   Each layer does exactly ONE job, so you can reason about
   them independently.

   ★ Retry INSIDE the semaphore is deliberate: a task holds its
     slot across its retries instead of releasing and re-queueing,
     which keeps concurrency genuinely capped.
```

### Exercise

Fetch 50 "tables" concurrently, capped at 8 at a time, each with a 2-second timeout, retrying twice on failure, collecting successes and failures separately, and printing a summary at the end.

This is a real ingestion job in about 40 lines.

### Solution

```python
import asyncio
import logging
import random

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
logger = logging.getLogger("ingest")

MAX_CONCURRENT = 8
TIMEOUT_SECONDS = 2
MAX_ATTEMPTS = 3

async def fetch_table(name: str) -> dict:
    """Simulated source: sometimes slow, sometimes broken."""
    await asyncio.sleep(random.uniform(0.1, 0.5))
    roll = random.random()
    if roll < 0.15:
        raise ConnectionError(f"{name}: connection reset")
    if roll < 0.20:
        await asyncio.sleep(5)          # will hit the timeout
    return {"table": name, "rows": random.randint(100, 10_000)}

async def fetch_with_retry(name: str) -> dict:
    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            async with asyncio.timeout(TIMEOUT_SECONDS):
                return await fetch_table(name)
        except (ConnectionError, TimeoutError) as exc:
            if attempt == MAX_ATTEMPTS:
                logger.error("%s: giving up after %d attempts (%s)", name, attempt, exc)
                raise
            delay = 0.2 * (2 ** (attempt - 1)) + random.uniform(0, 0.2)
            logger.warning("%s: attempt %d failed (%s), retry in %.2fs",
                           name, attempt, exc, delay)
            await asyncio.sleep(delay)

async def fetch_guarded(sem: asyncio.Semaphore, name: str) -> dict:
    async with sem:
        return await fetch_with_retry(name)

async def main() -> None:
    tables = [f"table_{i:02d}" for i in range(50)]
    sem = asyncio.Semaphore(MAX_CONCURRENT)

    results = await asyncio.gather(
        *(fetch_guarded(sem, t) for t in tables),
        return_exceptions=True,
    )

    succeeded = [r for r in results if not isinstance(r, Exception)]
    failed = [(t, r) for t, r in zip(tables, results) if isinstance(r, Exception)]

    logger.info("=" * 50)
    logger.info("loaded  : %d tables", len(succeeded))
    logger.info("rows    : %s", f"{sum(r['rows'] for r in succeeded):,}")
    logger.info("failed  : %d tables", len(failed))
    for name, exc in failed:
        logger.info("   %s -> %s", name, type(exc).__name__)

asyncio.run(main())
```

Check your version against the layering: is the retry inside the semaphore, or outside? Outside means a task releases its slot between attempts and has to queue again — concurrency is no longer really capped at 8 while retries are in flight.

# Part 2 — Regex

## 13. What regex actually is

### Explain

A regex is a **pattern that describes what text should look like**. You hand it to Python and ask "does this match?" or "pull out the bits that match."

For a data engineer it earns its keep in five places:

```
  1. parsing log lines             "2026-08-22 ERROR [orders-etl] job_id=4412"
  2. validating IDs and codes      "ORD-20260822-4412"  ✓   "ORD-123"  ✗
  3. extracting fields from paths  "s3://lake/orders/dt=2026-08-22/part-01.parquet"
  4. cleaning column names         " Total Revenue ($CAD) " → "total_revenue_cad"
  5. finding bad rows in dirty source data
```

> **Trap.** Always use raw strings. Write `r"\d+"`, never `"\d+"`. In a normal string, `\d` may be interpreted by Python before regex ever sees it. The `r` prefix says "hands off, pass this through untouched." This habit removes an entire category of confusing bug.

### Exercise

Without running anything: which of these will behave as intended, and why?

```python
a = re.search("\d+", "abc 123")
b = re.search(r"\d+", "abc 123")
c = re.search("\bid\b", "the id column")
d = re.search(r"\bid\b", "the id column")
```

### Solution

- **`a`** — works *by accident*. `\d` isn't a recognised Python escape, so Python leaves it alone and regex sees `\d`. (Newer Pythons emit a `SyntaxWarning` for this.)
- **`b`** — correct and intentional. ✅
- **`c`** — **broken**. `\b` *is* a recognised Python escape: it's the backspace character `\x08`. Regex receives a literal backspace, not a word boundary, and the match fails.
- **`d`** — correct. ✅

`c` is exactly why the rule is "always raw strings" rather than "raw strings when needed" — the failure is silent and you can't tell by looking.

## 14. The building blocks

### Explain

Learn these fifteen and you can read almost any pattern.

```
  WHAT to match                    HOW MANY                WHERE
  ─────────────                    ────────                ─────
  \d  any digit          7         *    zero or more       ^   start of string
  \w  letter/digit/_     a 9 _     +    one or more        $   end of string
  \s  any whitespace     ␣ \t \n   ?    zero or one        \b  word boundary
  .   any character      anything  {3}  exactly 3
  [abc] one of a,b,c     b         {2,5} between 2 and 5
  [a-z] any lowercase    q         {3,}  3 or more
  [^abc] anything EXCEPT z

  Capitals invert:  \D = not a digit   \S = not whitespace   \W = not word char
```

`\b` is the underrated one. `r"\bid\b"` matches the word "id" but **not** the "id" inside "invalid" or "identity".

**Read a pattern left to right, out loud, in plain English:**

```
   r"^\d{4}-\d{2}-\d{2}$"
    ^      start of string
    \d{4}  four digits
    -      a literal dash
    \d{2}  two digits
    -      a dash
    \d{2}  two digits
    $      end of string

   → a date check, anchored both ends,
     so "2026-08-22 extra junk" correctly FAILS
```

### Exercise

Write patterns matching **exactly** these, anchored at both ends:
(a) a 4-digit year; (b) a Canadian postal code (`K1A 0B1`, space optional); (c) an order ID like `ORD-20260822-4412`; (d) a Snowflake-style identifier (letters, digits, underscores, must **not** start with a digit).

### Solution

```python
import re

YEAR        = re.compile(r"^\d{4}$")
POSTAL_CODE = re.compile(r"^[A-Z]\d[A-Z] ?\d[A-Z]\d$")
ORDER_ID    = re.compile(r"^ORD-\d{8}-\d{4}$")
IDENTIFIER  = re.compile(r"^[A-Za-z_]\w*$")

assert YEAR.match("2026") and not YEAR.match("202")
assert POSTAL_CODE.match("K1A 0B1") and POSTAL_CODE.match("K1A0B1")
assert ORDER_ID.match("ORD-20260822-4412")
assert IDENTIFIER.match("_orders_v2") and not IDENTIFIER.match("2orders")
```

`\w*` after the first character allows letters, digits and underscores, but the leading `[A-Za-z_]` blocks a digit at the start. That mirrors how most SQL engines treat unquoted identifiers.

The ` ?` in the postal code means "an optional single space" — that's how you make a separator optional without allowing multiple.

## 15. Groups

### Explain

Round brackets **capture** a piece so you can retrieve it.

```
   r"(?P<year>\d{4})-(?P<month>\d{2})-(?P<day>\d{2})"
       └──┬──┘         └──┬───┘         └─┬─┘
          │               │               │
     ┌────▼────┐    ┌─────▼────┐    ┌─────▼───┐
     │ "2026"  │    │  "08"    │    │  "22"   │
     └─────────┘    └──────────┘    └─────────┘

   m.group("year")  → '2026'
   m.groupdict()    → {'year':'2026','month':'08','day':'22'}   ← ready-made dict
   m.group(0)       → '2026-08-22'   (the WHOLE match)
```

**Named groups are better than numbered ones**, for two reasons:

1. Six months later, `m.group("job_id")` still reads clearly; `m.group(4)` doesn't.
2. When someone adds a bracket to the pattern, **positional numbers all shift** and your code silently reads the wrong field. Named groups don't have that failure mode.

Use `(?:...)` when you need brackets for grouping but don't want to capture:

```python
r"(?:https?://)(?P<host>[^/]+)"    # the protocol is grouped but not captured
```

### Exercise

From `"2026-08-22 14:03:11 ERROR [orders-etl] job_id=4412 rows=0"`, use named groups to produce a dict with `ts`, `level`, `job`, `job_id`, and `rows`.

### Solution

```python
import re

LINE = re.compile(
    r"^(?P<ts>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2})\s+"
    r"(?P<level>\w+)\s+"
    r"\[(?P<job>[\w-]+)\]\s+"
    r"job_id=(?P<job_id>\d+)\s+"
    r"rows=(?P<rows>\d+)"
)

line = "2026-08-22 14:03:11 ERROR [orders-etl] job_id=4412 rows=0"
print(LINE.search(line).groupdict())
# {'ts': '2026-08-22 14:03:11', 'level': 'ERROR', 'job': 'orders-etl',
#  'job_id': '4412', 'rows': '0'}
```

> **Tip.** Notice the pattern is split across several adjacent string literals — Python joins them automatically, so each piece gets its own line. **Do this.** Long regexes on one line are unreadable and unreviewable.

> **Trap.** Everything comes back as a **string**. Cast in a separate step so a bad value produces a clear error:

```python
d = LINE.search(line).groupdict()
d["rows"] = int(d["rows"])
```

## 16. The five functions

### Explain

```python
text = "job_id=4412 rows=0 status=FAILED"

re.search(r"rows=(\d+)", text)      # first match ANYWHERE → Match or None
re.match(r"job_id", text)           # only at the START    → Match or None
re.findall(r"(\w+)=(\S+)", text)    # every match → list
re.finditer(r"(\w+)=(\S+)", text)   # every match → iterator of Match objects
re.sub(r"\d+", "N", text)           # replace → 'job_id=N rows=N status=FAILED'
re.split(r"\s+", text)              # split   → ['job_id=4412', 'rows=0', ...]
```

```
   search  │◀─────── looks anywhere ───────▶│
   match   │◀─ only here                     │
           └─────────────────────────────────┘
            job_id=4412 rows=0 status=FAILED
```

**`search` vs `match`.** `match` only looks at the start. Most of the time you want `search`. Reaching for `match` and getting `None` on text that obviously contains your pattern is a rite of passage.

> **Trap.** Always check for `None`. `re.search` returns `None` when there's no match, and `None.group()` is an `AttributeError` at 3am.

```python
m = pattern.search(line)
if m is None:
    logger.warning("unparseable line: %s", line[:100])
    continue
```

> **Tip.** Name your patterns as module-level constants. Python caches recent patterns so the *speed* gain from `re.compile` is smaller than people claim, but readability is the real win.

### Exercise

Write `parse_log_line(line)` that returns a dict or `None`, then run it over a list of eight lines where three are malformed. Log the bad ones and return only the good ones.

### Solution

```python
import logging
import re

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

LINE = re.compile(
    r"^(?P<ts>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2})\s+"
    r"(?P<level>\w+)\s+"
    r"\[(?P<job>[\w-]+)\]"
)

def parse_log_line(line: str) -> dict | None:
    m = LINE.search(line)
    if m is None:
        return None
    return m.groupdict()

def parse_all(lines: list[str]) -> list[dict]:
    good, bad = [], 0
    for i, line in enumerate(lines):
        parsed = parse_log_line(line)
        if parsed is None:
            bad += 1
            logger.warning("line %d unparseable: %s", i, line[:60])
        else:
            good.append(parsed)
    logger.info("parsed %d lines, rejected %d", len(good), bad)
    return good

lines = [
    "2026-08-22 14:03:11 ERROR [orders-etl] job_id=1",
    "2026-08-22 14:03:12 INFO [orders-etl] job_id=2",
    "garbage line with no structure",                    # ✗
    "2026-08-22 14:03:13 WARN [payments-etl] job_id=3",
    "",                                                  # ✗
    "2026-08-22 14:03:14 INFO [orders-etl] job_id=4",
    "22/08/2026 14:03:15 INFO [orders-etl] job_id=5",    # ✗ wrong date format
    "2026-08-22 14:03:16 DEBUG [refunds-etl] job_id=6",
]
parse_all(lines)
```

**Returning `None` rather than raising is the right call here.** One bad line in a million shouldn't kill the job — but you do want it **counted and logged**. A silent skip is how you end up explaining missing data three weeks later.

## 17. Greedy vs lazy

### Explain

By default, quantifiers grab **as much as they possibly can**.

```
  text:  msg="first" other msg="second"

  GREEDY  r'msg="(.*)"'
          msg="│◀═══════════════════════▶│"
          captures: first" other msg="second      ← ran to the LAST quote

  LAZY    r'msg="(.*?)"'
          msg="│◀═══▶│"
          captures: first                          ← the ? = "take as little as possible"

  BEST    r'msg="([^"]*)"'
          msg="│◀═══▶│"
          captures: first                          ← "any chars that AREN'T a quote"
                                                     CANNOT cross a quote at all
```

The `?` after `*` or `+` means "take as little as possible." But there's usually a better fix than lazy matching: **say what you actually mean.**

`[^"]*` is clearer than `.*?`, and much faster, because the regex engine never has to backtrack.

### Exercise

Explain the difference in output between `r'msg="(.*)"'` and `r'msg="(.*?)"'` on a line containing two quoted messages. Then write a third version using a character class that's better than both.

### Solution

```python
import re

text = 'msg="first message" other stuff msg="second message"'

print(re.search(r'msg="(.*)"',   text).group(1))
# first message" other stuff msg="second message
print(re.search(r'msg="(.*?)"',  text).group(1))
# first message
print(re.search(r'msg="([^"]*)"', text).group(1))
# first message
```

Greedy `.*` runs to the end of the line and **backtracks** until it can find a final quote, so it swallows both messages. Lazy `.*?` stops at the first quote it can.

The third is better than the lazy version because `[^"]*` **cannot cross a quote at all**. It expresses the intent directly, needs no backtracking, and won't surprise you when the pattern grows.

## 18. Lookarounds

### Explain

Sometimes you need to **check what's around a match without including it** in the result.

```
   "total 4500 USD"                        "price $4500 net"
          ▲▲▲▲ ┄┄┄┄                              ┄ ▲▲▲▲
          │    └ (?=\s*USD)  "followed by"       │ └ captured
          └ captured                             └ (?<=\$) "preceded by"

   r"\d+(?=\s*USD)"  → '4500'              r"(?<=\$)\d+"  → '4500'
```

| Syntax | Means |
|---|---|
| `(?=...)` | followed by |
| `(?!...)` | **not** followed by |
| `(?<=...)` | preceded by |
| `(?<!...)` | **not** preceded by |

Useful, but don't reach for them first. A lookaround in a pattern is often a sign the job would be better done with **two simple steps than one clever one**.

### Exercise

Using a negative lookahead, find every occurrence of `ERROR` in a log that is **not** followed by `_RECOVERED`.

### Solution

```python
import re

log = "ERROR failed\nERROR_RECOVERED retry ok\nERROR timeout\nERROR_RECOVERED fine"
print(re.findall(r"ERROR(?!_RECOVERED)", log))
# ['ERROR', 'ERROR']
```

`(?!_RECOVERED)` checks what follows **without consuming it**, so the match itself is just `ERROR`.

Without the lookahead you'd get four matches, because `ERROR` is a prefix of `ERROR_RECOVERED`.

## 19. Real pipeline patterns

### Explain

Four patterns you'll write over and over.

**Parsing an S3 / data lake path** — extracting the partition date is something you'll do constantly:

```
  s3://prod-lake/raw/orders/dt=2026-08-22/part-00017.parquet
       └───┬────┘ └────┬───┘    └───┬────┘ └───────┬───────┘
        bucket      prefix          dt            file
```

**Cleaning column names for a warehouse** — every messy CSV needs this:

```
   " Total Revenue ($CAD) "  ──▶  anything odd → "_"  ──▶  collapse repeats
                             ──▶  strip + lower       ──▶  "total_revenue_cad"
```

**Extracting key=value pairs — and a real bug:**

```python
line = '2026-08-22 14:03:11 ERROR [orders-etl] job_id=4412 rows=0 msg="no data found"'

re.findall(r"(\w+)=(\S+)", line)
# [('job_id','4412'), ('rows','0'), ('msg','"no')]     ← ⚠ WRONG
```

`\S+` means "non-whitespace," so it stopped at the space **inside** the quoted message. The fix says a value is *either* a quoted string *or* a run of non-space characters:

```python
re.findall(r'(\w+)=("[^"]*"|\S+)', line)
# [('job_id','4412'), ('rows','0'), ('msg','"no data found"')]  ✓
```

**This is what regex debugging actually feels like.** The pattern works on your first three test lines and quietly mangles the fourth. Test against ugly real data, not clean examples.

**Validating before load:**

```python
PATTERNS = {
    "order_id":    re.compile(r"^ORD-\d{8}$"),
    "postal_code": re.compile(r"^[A-Z]\d[A-Z] ?\d[A-Z]\d$"),   # Canadian
    "email":       re.compile(r"^[^@\s]+@[^@\s]+\.[^@\s]+$"),
}
```

> **Trap.** On email specifically: do not go looking for the "complete" RFC-compliant email regex. It exists, it's thousands of characters long, and it's the wrong tool. Check for one `@` with something on each side and a dot after, then let the mail server be the real judge.

> **Tip.** Debugging tip: paste your pattern into regex101.com, choose the Python flavour, paste in real sample lines. It explains every token and highlights what matched.

**(a) Column cleaner**

```python
import re

def clean_column(name: str) -> str:
    name = name.strip()
    name = re.sub(r"[^0-9a-zA-Z]+", "_", name)   # anything odd becomes underscore
    name = re.sub(r"_+", "_", name)              # collapse repeats
    name = name.strip("_").lower()
    if re.match(r"^\d", name):
        name = f"col_{name}"
    return name

for raw in [" Total Revenue ($CAD) ", "Customer ID#", "2026 Sales",
            "order__id", "  ", "Amount (%)"]:
    print(f"{raw!r:28} -> {clean_column(raw)!r}")
```

```
'Customer ID#'               -> 'customer_id'
'2026 Sales'                 -> 'col_2026_sales'
'order__id'                  -> 'order_id'
'  '                         -> ''
'Amount (%)'                 -> 'amount'
```

The empty-string case is worth handling explicitly in real code — raise, or fall back to `col_{position}`.

**(b) Path parsing**

```python
PATH = re.compile(
    r"s3://(?P<bucket>[^/]+)/"
    r"(?P<dataset>.+?)/"
    r"dt=(?P<date>\d{4}-\d{2}-\d{2})/"
    r"hour=(?P<hour>\d{1,2})/"
    r"(?P<filename>[^/]+)$"
)

path = "s3://lake/raw/orders/dt=2026-08-22/hour=14/part-0001.parquet"

# {'bucket':'lake','dataset':'raw/orders','date':'2026-08-22',
#  'hour':'14','filename':'part-0001.parquet'}
```

`.+?` for the dataset is **lazy on purpose**. Greedy `.+` would swallow the `dt=` segment and then backtrack, and on deeply nested paths it can pick the wrong split.

**(c) Masking emails**

```python
EMAIL = re.compile(r"\b([\w.+-]+)@([\w-]+\.[\w.-]+)\b")

def mask(match: re.Match) -> str:
    local, domain = match.group(1), match.group(2)
    return f"{local[0]}{'*' * (len(local) - 1)}@{domain}"

print(EMAIL.sub(mask, "contact a.patel@corp.com or ops@corp.com now"))
# contact a******@corp.com or o**@corp.com now
```

**Passing a function to `re.sub` is the trick worth remembering.** The function receives the `Match` object and returns the replacement, so the replacement can depend on what was matched. Useful for redaction, normalisation, and lookup-based substitution.

**(d) Row validator**

```python
PATTERNS = {
    "order_id":    re.compile(r"^ORD-\d{8}-\d{4}$"),
    "postal_code": re.compile(r"^[A-Z]\d[A-Z] ?\d[A-Z]\d$"),
    "amount":      re.compile(r"^\d+(\.\d{1,2})?$"),
}

def find_bad_rows(rows: list[dict]) -> list[tuple[int, str]]:
    problems = []
    for i, row in enumerate(rows):
        for field, pattern in PATTERNS.items():
            value = row.get(field)
            if value is None or not pattern.match(str(value)):
                problems.append((i, field))
    return problems

rows = [
    {"order_id": "ORD-20260822-4412", "postal_code": "K1A 0B1", "amount": "1250.00"},
    {"order_id": "ORD-123",           "postal_code": "K1A 0B1", "amount": "1250.00"},
    {"order_id": "ORD-20260822-4413", "postal_code": "90210",   "amount": "-50"},
    {"order_id": "ORD-20260822-4414", "postal_code": "M5V2T6",  "amount": "99.999"},
]
print(find_bad_rows(rows))
# [(1, 'order_id'), (2, 'postal_code'), (2, 'amount'), (3, 'amount')]
```

`^\d+(\.\d{1,2})?$` rejects negatives (no sign allowed) **and** more than two decimal places.

Returning `(index, field)` pairs rather than just "bad row" means the error message can name the actual problem — the difference between a useful quarantine table and a useless one.

## 20. The two traps

### Explain

**Trap 1 — catastrophic backtracking.** Some patterns are exponentially slow on certain inputs. The classic shape is **a repeat inside a repeat**.

```
   r"^(a+)+$"  against  "aaaaaaaaaaaaaaaaaaaaaaaaaaX"

   The engine tries EVERY possible way to divide the a's
   between the inner + and the outer +:

     (aaaa)(aaaa)(aaaa)...  ✗
     (aaaaaaaa)(aaaa)...    ✗
     (aa)(aa)(aa)(aa)...    ✗
     ... 2^n combinations ...

   25 characters → effectively frozen. Each extra char ≈ doubles the time.

   ❌ AVOID:  (x+)+   (x*)*   (x+)*
   ✅ USE:    x+      [^"]*   explicit character classes
```

**Trap 2 — regex is not a parser.** Don't parse JSON, XML, or HTML with regex. They're **nested**, and regex fundamentally cannot handle nesting. Use `json.loads`, `lxml`, `BeautifulSoup`.

Regex is for **flat, line-shaped text**, and it's excellent at that.

### Exercise

Time `re.match(r"^(a+)+$", "a" * 20 + "X")` and then `re.match(r"^a+$", "a" * 20 + "X")`. Explain the gap in one sentence.

### Solution

```python
import re
import time

for n in (18, 20, 22, 24):
    text = "a" * n + "X"

    start = time.perf_counter()
    re.match(r"^(a+)+$", text)
    nested = time.perf_counter() - start

    start = time.perf_counter()
    re.match(r"^a+$", text)
    simple = time.perf_counter() - start

    print(f"n={n}: nested {nested:8.4f}s   simple {simple:.6f}s")
```

**One sentence:** `(a+)+` gives the engine exponentially many ways to divide the same run of `a`s between the inner and outer repeat, so when the final `X` forces failure it has to try every one of them, while `a+` has only a single way to match and fails instantly.

Each extra character roughly doubles the time. Around n=25 you're waiting minutes.

**The rule that follows: never nest one quantifier inside another.** If a pattern is ever mysteriously slow, this is why.

## 21. Generators

### Explain

A generator produces values **one at a time** instead of building a list. `yield` instead of `return`.

```
   LIST                              GENERATOR
   ────                              ─────────
   ┌───────────────────────┐         ┌───┐
   │ row row row row row   │         │row│ → process → next
   │ row row row row row   │         └───┘
   │ ... all 10 GB in RAM  │         one row at a time
   └───────────────────────┘         RAM stays flat
   💥 dies on a big file             ✓ works on any size
```

```python
# Loads the entire file into memory. Dies on a 10 GB file.
def read_all(path):
    with open(path) as f:
        return [parse(line) for line in f]

# Holds one line at a time. Works on any size file.
def read_rows(path):
    with open(path) as f:
        for line in f:
            yield parse(line)
```

**Generators chain**, and each stage still holds only one row:

```
   read_rows ──▶ drop_nulls ──▶ enrich ──▶ write
      ▓             ▓             ▓          ▓
   one row       one row       one row    one row

   Nothing runs until you iterate. Lazy all the way down.
   (Same mental model as a Spark DAG — a useful thing to say in an interview.)
```

```python
pipeline = enrich(drop_nulls(read_rows("huge.csv")))
for row in pipeline:
    write(row)
```

> **Trap.** The gotcha: a generator is **consumed once**. Iterate it twice and the second loop sees nothing. If you need multiple passes, materialise it with `list()` and accept the memory cost, or read the source again.

**(b)** Chain three generators: read → filter out rows where `amount <= 0` → add a `loaded_at` field. Consume it and count. Confirm no intermediate list is ever built.

**(a)**

```python
    for i in range(n):

tracemalloc.stop()

tracemalloc.start()
rows = [{"id": i, "amount": i * 1.5} for i in range(N)]
total2 = sum(row["amount"] for row in rows)

print(f"list peak:      {list_peak / 1024 / 1024:8.2f} MB")

```

The generator peak stays in **kilobytes**. The list peak runs to **hundreds of megabytes**. Same answer, and one of them scales to a file that doesn't fit in RAM.

**(b)**

```python
from datetime import datetime, UTC

def read_rows(n: int):
    for i in range(n):
        yield {"id": i, "amount": (i % 7) - 3}

def drop_non_positive(rows):
    for row in rows:
        if row["amount"] > 0:
            yield row

def add_loaded_at(rows):
    stamp = datetime.now(UTC)
    for row in rows:
        yield {**row, "loaded_at": stamp}

pipeline = add_loaded_at(drop_non_positive(read_rows(100)))

```

**Nothing runs until `sum` starts iterating.** Each row travels the full chain before the next is read, so memory holds one row regardless of source size.

## 22. Batching

### Explain

Inserting one row at a time into a warehouse is **death by network round-trip**. Batch it.

```
   ROW BY ROW                          BATCHED (1000 at a time)
   ──────────                          ────────────────────────
   ●─────▶ warehouse  (30ms)           ●●●●●●●●●●─────▶ warehouse (35ms)
   ●─────▶ warehouse  (30ms)           ●●●●●●●●●●─────▶ warehouse (35ms)
   ●─────▶ warehouse  (30ms)
   × 1,000,000 = 8 hours               × 1,000 = 35 seconds
```

Python 3.12 gives you this for free:

```python
from itertools import batched

for chunk in batched(read_rows("huge.csv"), 1000):
    warehouse.insert_many(chunk)      # chunk is a tuple of up to 1000 rows
```

Under 3.12, write it yourself — worth knowing anyway:

```python
from itertools import islice

def batched(iterable, n):
    it = iter(iterable)
    while chunk := tuple(islice(it, n)):
        yield chunk
```

Combines directly with async:

```python
async def load_all(rows, batch_size=1000, concurrency=5):
    sem = asyncio.Semaphore(concurrency)

    async def load_one(chunk):
        async with sem:
            await warehouse.insert_many(chunk)

    await asyncio.gather(*(load_one(c) for c in batched(rows, batch_size)))
```

That's **generators for memory, batching for throughput, and async for concurrency, in nine lines.** It's most of what an ingestion job is.

### Exercise

Implement `batched()` yourself with `islice`. Test it on 10 items with size 3 and confirm the last batch has 1.

### Solution

```python
from itertools import islice

def batched(iterable, n: int):
    if n < 1:
        raise ValueError("n must be at least 1")
    it = iter(iterable)
    while chunk := tuple(islice(it, n)):
        yield chunk

for chunk in batched(range(10), 3):
    print(len(chunk), chunk)
# 3 (0, 1, 2)
# 3 (3, 4, 5)
# 3 (6, 7, 8)
# 1 (9,)
```

> **Trap.** `iter(iterable)` at the top is essential. Without it, `islice` would restart from the beginning of a list every time and you'd loop forever.

The walrus `:=` assigns and tests in one step; the loop ends when `islice` returns an empty tuple.

## 23. Context managers

### Explain

`with` blocks **guarantee cleanup runs, even on an exception.**

```
   @contextmanager
   def timed(label):
       start = ...          ┐
       logger.info(...)     ├── SETUP     (everything before yield)
       try:                 ┘
           yield            ←── the `with` body runs HERE
       finally:             ┐
           logger.info(...) ├── TEARDOWN  (everything after yield)
                            ┘   `finally` = runs even if the body RAISES
```

```python
from contextlib import contextmanager
import time, logging

logger = logging.getLogger(__name__)

@contextmanager
def timed(label: str):
    start = time.perf_counter()
    logger.info("%s starting", label)
    try:
        yield
    finally:
        logger.info("%s finished in %.2fs", label, time.perf_counter() - start)

with timed("extract orders"):
    rows = extract()
```

A more useful one — transaction handling:

```python
@contextmanager
def transaction(conn):
    conn.execute("BEGIN")
    try:
        yield conn
        conn.execute("COMMIT")
    except Exception:
        conn.execute("ROLLBACK")
        raise
```

Async version uses `@asynccontextmanager` and `async with`.

**(b)** Write a `@contextmanager` simulating a database transaction with a fake connection object that records `["BEGIN", "COMMIT"]` or `["BEGIN", "ROLLBACK"]`. Test both paths.

### Solution

**(a)**

```python

import time
from contextlib import contextmanager

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")

@contextmanager
def timed(label: str):
    start = time.perf_counter()
    logger.info("%s starting", label)
    try:
        yield
    finally:
        logger.info("%s finished in %.3fs", label, time.perf_counter() - start)

with timed("clean run"):
    time.sleep(0.1)

try:
    with timed("failing run"):
        time.sleep(0.05)
        raise ValueError("boom")
except ValueError:
    print("caught it, but the timing still logged")
```

**The `finally` is what makes it reliable.** Without it, an exception would skip the teardown and you'd lose timing data on exactly the runs you most want to investigate.

**(b)**

```python

    def __init__(self):
        self.log = []

    def execute(self, sql: str):
        self.log.append(sql)

@contextmanager

    conn.execute("BEGIN")
    try:
        yield conn
        conn.execute("COMMIT")
    except Exception:
        conn.execute("ROLLBACK")
        raise

conn = FakeConnection()
with transaction(conn) as c:
    c.execute("INSERT INTO orders VALUES (1)")
print(conn.log)   # ['BEGIN', 'INSERT INTO orders VALUES (1)', 'COMMIT']
```

## 24. Dataclasses

### Explain

Dicts everywhere means typos are **silent**. `row["custommer_id"]` is a `KeyError` at runtime — or worse, a `.get()` that quietly returns `None`.

```
   DICT                                 DATACLASS
   ────                                 ─────────
   row["custommer_id"]                  row.custommer_id
        ↑ typo                               ↑ typo
   KeyError at 3am, or a silent None    AttributeError immediately,
                                        and your IDE catches it first
```

```python
from dataclasses import dataclass, field
from datetime import datetime, UTC

@dataclass(frozen=True, slots=True)
class OrderRow:
    order_id: str
    amount: float
    currency: str = "CAD"
    loaded_at: datetime = field(default_factory=lambda: datetime.now(UTC))

    def __post_init__(self):
        if self.amount < 0:
            raise ValueError(f"negative amount on {self.order_id}")
```

- **`frozen=True`** — immutable, so nothing downstream can silently mutate a row.
- **`slots=True`** — cuts memory substantially, which matters at a million rows.
- **`field(default_factory=...)`** — required for mutable or computed defaults.
- **`__post_init__`** — runs after construction; the natural place for validation.

> **Trap.** The mutable default bug:

```
   loaded_at: datetime = datetime.now()      ← evaluated ONCE, at class definition
                                                EVERY instance gets the timestamp
                                                of program start. Nothing errors.
                                                A 6-hour job stamps every row the same.

   loaded_at: datetime = field(default_factory=lambda: datetime.now(UTC))   ✓
                                                evaluated per instance
```

For anything crossing a system boundary (an API response, a config file), use **Pydantic** instead — it coerces types and gives readable errors. **Dataclasses for internal structures, Pydantic for untrusted input.**

### Exercise

**(a)** Build an `OrderRow` dataclass with `frozen=True`, `slots=True`, a `default_factory` timestamp, and `__post_init__` validation rejecting negative amounts. Prove `frozen` works by trying to reassign a field.

**(b)** Demonstrate the mutable default bug: build a dataclass with a list default using `field(default_factory=list)`, then explain in a comment what would go wrong with a bare `= []`.

### Solution

**(a)**

```python
from dataclasses import dataclass, field, FrozenInstanceError
from datetime import datetime, UTC

@dataclass(frozen=True, slots=True)
class OrderRow:
    order_id: str
    amount: float
    currency: str = "CAD"
    loaded_at: datetime = field(default_factory=lambda: datetime.now(UTC))

    def __post_init__(self):
        if self.amount < 0:
            raise ValueError(f"negative amount on {self.order_id}: {self.amount}")
        if not self.order_id:
            raise ValueError("order_id is required")

row = OrderRow("ORD-1", 1250.00)
print(row)

try:
    row.amount = 99
except FrozenInstanceError:
    print("frozen: cannot reassign")

try:
    OrderRow("ORD-2", -5)
except ValueError as e:
    print(f"validation: {e}")
```

> **Tip.** `__post_init__` works with `frozen=True` because it only *reads* the fields. If you needed to *modify* one inside `__post_init__` on a frozen dataclass you'd have to use `object.__setattr__(self, "field", value)` — a strong hint your design wants a classmethod constructor instead.

**(b)**

```python
    #     loaded_at: datetime = datetime.now()

    # instance creation, which is what you actually want.
```

## 25. Retry, synchronously

### Explain

The synchronous-code sibling of [1.7](#17--retry-with-backoff). Same three rules:

```
   1. EXPONENTIAL   1s, 2s, 4s, 8s — a struggling service needs room
   2. JITTER        + random(0,1) — or 200 workers retry in lockstep
   3. BE SPECIFIC   retry_on=(ConnectionError, TimeoutError)
                    A 503 is worth retrying. A 401 or a schema mismatch
                    will fail identically five times, wasting 15 seconds.
```

```python
async def with_retry(fn, *args, attempts=5, base_delay=1.0,
                     retry_on=(ConnectionError, TimeoutError)):
    for attempt in range(1, attempts + 1):
        try:
            return await fn(*args)
        except retry_on as exc:
            if attempt == attempts:
                logger.error("giving up after %d attempts: %s", attempts, exc)
                raise
            delay = base_delay * (2 ** (attempt - 1)) + random.uniform(0, 1)
            logger.warning("attempt %d failed (%s), retrying in %.1fs",
                           attempt, exc, delay)
            await asyncio.sleep(delay)
```

> **Tip.** In production use the **`tenacity`** library rather than hand-rolling. Write it yourself once, then use the library.

### Exercise

### Solution

```python
import asyncio
import logging
import random

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
logger = logging.getLogger(__name__)

async def with_retry(fn, *args, attempts=5, base_delay=0.1,
                     retry_on=(ConnectionError, TimeoutError)):
    for attempt in range(1, attempts + 1):
        try:
            return await fn(*args)
        except retry_on as exc:
            if attempt == attempts:
                logger.error("gave up after %d attempts: %s", attempts, exc)
                raise
            delay = base_delay * (2 ** (attempt - 1)) + random.uniform(0, base_delay)
            logger.warning("attempt %d failed (%s), retry in %.3fs", attempt, exc, delay)
            await asyncio.sleep(delay)

def make_flaky(fail_times: int):
    state = {"calls": 0}

    async def flaky():
        state["calls"] += 1
        if state["calls"] <= fail_times:
            raise ConnectionError(f"failure {state['calls']}")
        return f"ok after {state['calls']} calls"

    return flaky, state

async def main():
    fn, state = make_flaky(2)
    print(await with_retry(fn))

    fn2, state2 = make_flaky(99)
    try:
        await with_retry(fn2, attempts=4)
    except ConnectionError:
        print(f"gave up correctly after {state2['calls']} calls")

asyncio.run(main())
```

> **Tip.** `make_flaky` returns a **closure over a mutable dict** instead of using `global`. Cleaner, and it lets you build several independent flaky functions in one test.

## 26. Logging, not printing

### Explain

`print` has no severity, no timestamp, no source, and can't be filtered or routed. **Every pipeline you write will eventually run unattended, and then logs are all you have.**

```
   print("loaded 5000 rows")
   → 5000 rows

   logger.info("loaded %d rows into %s", 5000, "orders")
   → 2026-08-22 14:03:11 INFO [etl.load] loaded 5000 rows into orders
     └── when ──────────┘ └sev┘ └─where─┘ └─────── what ───────┘
```

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s [%(name)s] %(message)s",
)
logger = logging.getLogger(__name__)

logger.info("loaded %d rows into %s", len(rows), table)      # ← note the COMMAS
logger.warning("skipped %d malformed rows", bad_count)
logger.error("load failed for %s", table, exc_info=True)     # includes traceback
```

Two habits worth forming now:

**Use `%s` with commas, not f-strings.** `logger.info("loaded %d rows", n)` only formats the string if that level is actually enabled, and log aggregators can group by the **message template**. `logger.info(f"loaded {n} rows")` formats every time and produces a million unique message strings you can't group.

**`logger = logging.getLogger(__name__)` at the top of every module.** You get per-module filtering for free, so you can turn a noisy library down to WARNING without silencing your own code.

### Exercise

Configure logging with the format above. Log one line at each of INFO, WARNING and ERROR (the last with `exc_info=True` inside an `except`). Then set the level to WARNING and confirm the INFO line disappears.

### Solution

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s [%(name)s] %(message)s",
)
logger = logging.getLogger(__name__)

logger.info("loaded %d rows into %s", 12345, "orders")
logger.warning("skipped %d malformed rows", 7)

try:
    1 / 0
except ZeroDivisionError:
    logger.error("load failed for %s", "orders", exc_info=True)

logging.getLogger().setLevel(logging.WARNING)
logger.info("this will not appear")
logger.warning("this will")
```

`exc_info=True` attaches the full traceback. `logger.exception(...)` is shorthand for exactly the same thing inside an `except` block.

## 27. Caching lookups

### Explain

```python
from functools import lru_cache

@lru_cache(maxsize=1000)
def get_currency_rate(code: str, date: str) -> float:
    return expensive_api_lookup(code, date)
```

```
   call 1: get_rate("USD","2026-08-22")  → 100ms  (miss, calls the API)
   call 2: get_rate("USD","2026-08-22")  → 0.0ms  (hit, returns instantly)
   call 3: get_rate("EUR","2026-08-22")  → 100ms  (miss — different key)
```

Ideal for dimension lookups repeated across many rows.

Two rules:

1. **Arguments must be hashable** — no lists or dicts; use tuples.
2. **Don't cache anything that changes.** A cached "current" exchange rate that's four hours stale is a bug you'll debug for a long time. **Cache lookups keyed by date, not lookups of "now".**

### Exercise

Add `@lru_cache` to a function that sleeps 0.1s. Call it 100 times with 5 distinct arguments. Time it, then print `func.cache_info()`.

### Solution

```python
import time
from functools import lru_cache

@lru_cache(maxsize=None)
def get_rate(currency: str) -> float:
    time.sleep(0.1)
    return {"CAD": 1.0, "USD": 1.35, "EUR": 1.47, "GBP": 1.71, "JPY": 0.009}[currency]

start = time.perf_counter()
for i in range(100):
    get_rate(["CAD", "USD", "EUR", "GBP", "JPY"][i % 5])
print(f"{time.perf_counter() - start:.3f}s")
print(get_rate.cache_info())
```

About **0.5s instead of 10s** — five real calls, ninety-five cache hits.

`cache_info()` shows `hits=95, misses=5`, and **that hit ratio is the number to watch.** A low ratio means your key has too much variety for caching to help, and you're just paying the memory cost for nothing.

## 28. Capstone: the whole pipeline

### Explain

Everything from all three parts, in one job:

```
  ┌─ timed("orders ingestion") ──────────────────────────────────────┐
  │                                                                  │
  │  read_source()      generator, one row at a time                 │
  │       ↓                                                          │
  │  validate()         regex checks, rejected rows counted BY REASON│
  │       ↓                                                          │
  │  batched(100)       chunks for throughput                        │
  │       ↓                                                          │
  │  ┌─ Semaphore(5) ──────────────────────────────────┐             │
  │  │   ┌─ retry (3 attempts, exponential + jitter) ─┐│             │
  │  │   │      write_batch()                         ││             │
  │  │   └────────────────────────────────────────────┘│             │
  │  └─────────────────────────────────────────────────┘             │
  │       ↓                                                          │
  │  logged summary: read / rejected(by reason) / loaded / failed    │
  └──────────────────────────────────────────────────────────────────┘
```

### Exercise

Build `pipeline.py` combining everything: a generator reading rows from a fake source, a regex validator marking bad rows, `batched()` for chunking, `asyncio` with a `Semaphore` to "load" chunks concurrently, retry with backoff on simulated failures, a `timed()` context manager around the whole thing, and a logged summary of rows read, rows rejected, batches loaded and batches failed.

> **Tip.** This is the one to put on GitHub. It's a genuine ingestion job and a better portfolio piece than most tutorials produce.

### Solution

```python
"""pipeline.py — a small but complete ingestion job."""

import asyncio
import logging
import random
import re
import time
from contextlib import contextmanager
from dataclasses import dataclass, field
from datetime import datetime, UTC
from itertools import islice

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
logger = logging.getLogger("pipeline")

BATCH_SIZE = 100
MAX_CONCURRENT = 5
MAX_ATTEMPTS = 3

ORDER_ID = re.compile(r"^ORD-\d{8}-\d{4}$")
AMOUNT = re.compile(r"^\d+(\.\d{1,2})?$")

# ---------- stats ----------

@dataclass
class Stats:
    read: int = 0
    rejected: int = 0
    batches_loaded: int = 0
    batches_failed: int = 0
    reasons: dict = field(default_factory=dict)

    def reject(self, reason: str) -> None:
        self.rejected += 1
        self.reasons[reason] = self.reasons.get(reason, 0) + 1

# ---------- utilities ----------

@contextmanager
def timed(label: str):
    start = time.perf_counter()
    logger.info("%s starting", label)
    try:
        yield
    finally:
        logger.info("%s finished in %.2fs", label, time.perf_counter() - start)

def batched(iterable, n: int):
    it = iter(iterable)
    while chunk := tuple(islice(it, n)):
        yield chunk

# ---------- extract ----------

def read_source(n: int, stats: Stats):
    """Generator: one row at a time, some deliberately malformed."""
    for i in range(n):
        stats.read += 1
        roll = random.random()
        if roll < 0.05:
            yield {"order_id": f"BAD-{i}", "amount": "100.00"}
        elif roll < 0.10:
            yield {"order_id": f"ORD-20260822-{i:04d}", "amount": "-99"}
        else:
            yield {"order_id": f"ORD-20260822-{i:04d}",
                   "amount": f"{random.uniform(10, 999):.2f}"}

# ---------- validate ----------

def validate(rows, stats: Stats):
    for row in rows:
        if not ORDER_ID.match(row["order_id"]):
            stats.reject("bad_order_id")
            continue
        if not AMOUNT.match(row["amount"]):
            stats.reject("bad_amount")
            continue
        yield {**row, "amount": float(row["amount"]), "loaded_at": datetime.now(UTC)}

# ---------- load ----------

async def write_batch(chunk: tuple) -> int:
    await asyncio.sleep(random.uniform(0.05, 0.2))
    if random.random() < 0.20:
        raise ConnectionError("warehouse connection reset")
    return len(chunk)

async def write_with_retry(chunk: tuple) -> int:
    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            return await write_batch(chunk)
        except ConnectionError as exc:
            if attempt == MAX_ATTEMPTS:
                raise
            delay = 0.1 * (2 ** (attempt - 1)) + random.uniform(0, 0.1)
            logger.warning("batch retry %d after %s, waiting %.2fs", attempt, exc, delay)
            await asyncio.sleep(delay)

async def load_all(batches, stats: Stats) -> None:
    sem = asyncio.Semaphore(MAX_CONCURRENT)

    async def guarded(chunk):
        async with sem:
            return await write_with_retry(chunk)

    results = await asyncio.gather(
        *(guarded(c) for c in batches),
        return_exceptions=True,
    )
    for r in results:
        if isinstance(r, Exception):
            stats.batches_failed += 1
            logger.error("batch permanently failed: %s", r)
        else:
            stats.batches_loaded += 1

# ---------- orchestrate ----------

async def main() -> None:
    stats = Stats()
    with timed("orders ingestion"):
        rows = read_source(5_000, stats)
        clean = validate(rows, stats)
        batches = list(batched(clean, BATCH_SIZE))   # see note below
        await load_all(batches, stats)

    logger.info("=" * 46)
    logger.info("rows read      : %s", f"{stats.read:,}")
    logger.info("rows rejected  : %s %s", f"{stats.rejected:,}", stats.reasons)
    logger.info("batches loaded : %d", stats.batches_loaded)
    logger.info("batches failed : %d", stats.batches_failed)

if __name__ == "__main__":
    asyncio.run(main())
```

**Two design notes, because they're the parts people get wrong:**

**Why `list(batched(...))`.** The read→validate→batch chain is a lazy generator, which is exactly what you want for memory. But `asyncio.gather` needs all the coroutines up front, and a plain generator can't be safely pulled from by several concurrent tasks. Materialising the list of batches is the pragmatic fix at this scale. For a genuinely huge source you'd instead feed the generator into an `asyncio.Queue` with a `maxsize` and let a fixed pool of workers pull from it — the pattern from [1.9](#19--queues--producer-and-consumer) — which keeps memory bounded end to end.

**Why rejected rows are counted by reason.** "3,000 rows rejected" tells you something is wrong. "2,940 bad_amount, 60 bad_order_id" tells you an upstream currency column changed format. The dict costs one line and saves an afternoon.

## When something breaks

1. **Read the last line of the traceback first.** It names the actual error.
2. **`<coroutine object ...>` in your output** → a missing `await`.
3. **Async code taking exactly as long as sync code** → a blocking call hiding in there.
4. **`AttributeError: 'NoneType' object has no attribute 'group'`** → your regex didn't match. Print the input line and check it on regex101.
5. **A regex that's mysteriously slow** → you nested a quantifier: `(x+)+`.
6. **Memory climbing through a "streaming" job** → you materialised a generator somewhere, or your queue has no `maxsize`.
