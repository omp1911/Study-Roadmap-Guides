# Part A — Your own OSDK app

## 1. What OSDK actually is

### Explain

Your Ontology is the shared set of "things" in Foundry — Flights, Orders, Equipment. **Workshop** is one way to build a screen on top of them: you drag widgets around in a browser and Foundry generates the app.

**OSDK is the other way.** Foundry generates a **typed npm package** for your specific Ontology, and you write ordinary React code against it. Same data, same permissions, same Actions — your own frontend.

```
                    ┌──────────────────────────────┐
                    │       THE ONTOLOGY           │
                    │  Order · Flight · Equipment  │
                    │  + Action types              │
                    └───────────┬──────────────────┘
                                │  one source of truth
                ┌───────────────┴────────────────┐
                │                                │
      ┌─────────▼──────────┐          ┌──────────▼───────────┐
      │  WORKSHOP APP      │          │  YOUR OSDK APP       │
      │  drag-and-drop     │          │  React on localhost  │
      │  built in browser  │          │  npm install <pkg>   │
      └────────────────────┘          └──────────────────────┘
                │                                │
                └────── write via the SAME ──────┘
                         Action → both screens update

   ★ The demo moment: apply an Action in YOUR app,
     refresh the Workshop app, watch the change appear.
```

You'll use **exactly the same** object types and action types your Workshop app already uses. That's the point — you'll see the two apps hitting the same data.

**Prerequisite check:**

```bash
node --version   # must be 18 or higher
npm --version
```

If Node is old, install Node 20 LTS (or use `nvm`).

### Exercise

Explain, in two sentences you could say to a colleague, what OSDK gives you that Workshop doesn't — and what Workshop gives you that OSDK doesn't.

<details>
<summary><b>Show solution</b></summary>

> **OSDK** gives you a typed npm package for your Ontology so you can build any frontend you like — custom UX, your own component library, your own hosting — while still going through Foundry's permissions and Actions rather than around them.
>
> **Workshop** gives you speed and zero maintenance: no build pipeline, no OAuth wiring, no dependency upgrades, and a non-engineer can change the layout without a deploy.

The honest framing for a design review: **Workshop until the UX requirement can't be met by widgets.** OSDK is a real frontend codebase with all the ongoing cost that implies.
</details>

### Explain

Before touching code, write down four things from your existing Workshop app. You'll reuse exactly these.

```
   ┌─────────────────────────────────────────────────────────────┐
   │ 1. The Ontology OBJECT TYPE it displays  (e.g. Order)       │
   │                                                             │
   │ 2. Its API NAME — not the display name  ⚠                   │
```

## 3. Create the app in Developer Console

### Explain

**Developer Console** is a separate app in the Foundry portal from Workshop. If you don't see it, it needs enabling at the enrollment level — ask your admin.

```
   Developer Console → + New application
   ┌──────────────────────────────────────────────────────────────────┐
   │ 1. BASIC INFO      name + icon                                   │
   │                    (the icon appears on the OAuth consent screen) │
   │                                                                   │
   │ 2. APPLICATION TYPE  ▸ Client-facing application  ← choose this  │
   │                        = a PUBLIC OAuth client, correct for a     │
   │                          browser app                              │
   │                      ▸ Backend service                            │
   │                        ⚠ do NOT also tick this, or web hosting    │
   │                          becomes unavailable later                │
   │                                                                   │
   │ 3. REDIRECT URL    http://localhost:8080/auth/callback            │
   │                                                                   │
   │ 4. RESOURCES       ▸ Yes, generate an Ontology SDK                │
   │                      select your Ontology                         │
   │                      select object types + action types (from A2) │
   │                      ⚠ the Ontology binding CANNOT be changed     │
   │                        after generation. Object/action selections │
   │                        CAN be changed by regenerating.            │
   └──────────────────────────────────────────────────────────────────┘
```

You land on the application **Overview** page. Copy **four values** into a scratch file — you need all of them:

| Value | Where |
|---|---|
| Client ID | Overview page |
| Foundry URL | e.g. `https://yourorg.palantirfoundry.com` |
| npm registry URL | Overview page, under SDK install instructions |
| Ontology RID | Ontology Manager → your ontology → Ontology configuration → Ontology metadata |

## 4. CORS

### Explain

This is where most first attempts fail, with a confusing browser error.

```
   Your browser at http://localhost:8080
        │
        │  fetch → https://yourorg.palantirfoundry.com/api/...
        ▼
   ┌─────────────────────────────────────────────┐
   │ Foundry: "is localhost:8080 on my allowed   │
   │           origins list?"                    │
   │                                             │
   │   NO  → browser blocks it. CORS error.      │
   │         Nothing in your code is wrong.      │
   │   YES → request goes through.               │
   └─────────────────────────────────────────────┘
```

**Option A (preferred):** Control Panel → CORS policy → add origin `http://localhost:8080`.

**Option B (if you don't have Control Panel rights — common on Developer Tier / restricted enrollments):** change the redirect URL in Developer Console to `https://localhost:8080/auth/callback` (note **https**) and run your dev server with HTTPS enabled:

```js
// vite.config.js
export default {
  server: { port: 8080, https: true }
}
```

You'll get a browser certificate warning on first load. Click through it.

### Exercise

Decide which option applies to you and apply it. Then predict: if you get CORS wrong, at what point in Part A will you find out — and what will the error look like?

<details>
<summary><b>Show solution</b></summary>

**You find out at Checkpoint 1 (A7)** — the first time your app tries to talk to Foundry. Not at install, not at build.

The error appears **in the browser console, not your terminal**, and reads something like:

```
Access to fetch at 'https://yourorg.palantirfoundry.com/...' from origin
'http://localhost:8080' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the requested resource.
```

> **Trap.** The trap: this error looks like a bug in your fetch code, and people spend an hour rewriting `foundryClient.ts`. **If the message contains the words "CORS policy", your code is fine** — it's an allowed-origins problem, and there are exactly two fixes (A and B above).

The other error you might see at the same point is `invalid redirect_uri`, which is a *different* problem — see [Troubleshooting](#troubleshooting-part-a).
</details>

## 5. Scaffold the project

### Explain

Everything from here on runs wherever you have **Node 20+** — your Foundry workspace terminal, your laptop, or the lab container. Two rules regardless of which:

- **Keep `FOUNDRY_TOKEN` out of your shell history and out of git.** Put it in a `.env` file, add `.env` to `.gitignore`, and load it with `set -a; source .env; set +a`.
- **If you're working in any kind of container or remote box, the dev server must bind `0.0.0.0`**, not `127.0.0.1`, or the port never reaches your browser: `npm run dev -- --host 0.0.0.0 --port 8080`.

```
   EASIEST PATH                          MANUAL PATH
   ────────────                          ───────────
   Developer Console → your app          npm create vite@latest my-osdk-app \
     → "Start developing" tab                 -- --template react-ts
                                          + write .npmrc yourself
   Shows a generated scaffold command     + export FOUNDRY_TOKEN
   pre-filled with YOUR client ID,        + npm install the pieces
   registry URL and package name.
                                          Use this if you want to see
   ✓ always current for your enrollment    every moving part.
   ✓ copy-paste, done
```

The scaffold (built on `@osdk/create-app`) gives you Vite + React + TypeScript with auth already wired.

**Manual path:** create a `.npmrc` in the project root — this lets npm pull your private SDK package from Foundry:

```
//<REGISTRY-URL-FROM-OVERVIEW-PAGE>:_authToken=${FOUNDRY_TOKEN}
<PACKAGE-NAME>:registry=https://<REGISTRY-URL-FROM-OVERVIEW-PAGE>
```

```bash
export FOUNDRY_TOKEN=<your-token>      # scoped token from the Dev Console app page
npm install @osdk/client @osdk/oauth
npm install <YOUR-GENERATED-PACKAGE-NAME>
```

> **Trap.** Never commit `FOUNDRY_TOKEN` or the token value to git. Add `.env` to `.gitignore`.

### Exercise

Scaffold the project and get `npm install` to complete successfully. If it fails with `401 Unauthorized`, diagnose it before reading the solution.

<details>
<summary><b>Show solution</b></summary>

A `401 Unauthorized` on `npm install` has exactly two causes:

1. **`FOUNDRY_TOKEN` isn't exported in this shell.** `.npmrc` uses `${FOUNDRY_TOKEN}` — if the variable is unset, npm sends an empty token. Check with `echo $FOUNDRY_TOKEN`. Note that a new terminal tab is a new shell; the export doesn't persist.
2. **The token expired.** Generate a fresh scoped token from the Developer Console app page.

A different failure — `404 Not Found` on the package rather than 401 — means the **registry line in `.npmrc` doesn't match the package name**. The second line scopes a specific package name to the Foundry registry; if the name is wrong, npm looks on public npmjs.com, doesn't find it, and 404s.

Verify with:

```bash
cat .npmrc          # both lines present? package name matches exactly?
echo $FOUNDRY_TOKEN # non-empty?
```
</details>

## 6. Wire up the client

### Explain

Two objects, created once, imported everywhere:

```
   ┌──────────────────────────────────────────────────────┐
   │  auth   = createPublicOauthClient(                   │
   │              CLIENT_ID, FOUNDRY_URL, REDIRECT)       │
   │           ↓ handles login redirects & token refresh  │
   │                                                       │
   │  client = createClient(FOUNDRY_URL, $ontologyRid,    │
   │                        auth)                          │
   │           ↓ every read and write goes through this   │
   └──────────────────────────────────────────────────────┘
              config comes from .env.local, NOT hardcoded
```

`src/foundryClient.ts`:

```ts
import { createClient } from "@osdk/client";
import { createPublicOauthClient } from "@osdk/oauth";
import { $ontologyRid } from "<YOUR-GENERATED-PACKAGE-NAME>";

const FOUNDRY_URL = import.meta.env.VITE_FOUNDRY_URL;
const CLIENT_ID   = import.meta.env.VITE_CLIENT_ID;
const REDIRECT    = import.meta.env.VITE_REDIRECT_URL; // http://localhost:8080/auth/callback

export const auth = createPublicOauthClient(CLIENT_ID, FOUNDRY_URL, REDIRECT);
export const client = createClient(FOUNDRY_URL, $ontologyRid, auth);
```

`.env.local` (gitignored):

```
VITE_FOUNDRY_URL=https://yourorg.palantirfoundry.com
VITE_CLIENT_ID=xxxxxxxx
VITE_REDIRECT_URL=http://localhost:8080/auth/callback
```

> 💡 If `$ontologyRid` isn't exported from your package, just paste the Ontology RID string directly.

### Exercise

Create `foundryClient.ts` and `.env.local`. Then answer: why must the env var names start with `VITE_`, and what happens if you name one `FOUNDRY_URL` instead?

<details>
<summary><b>Show solution</b></summary>

Vite only exposes env vars **prefixed with `VITE_`** to browser code via `import.meta.env`. Everything else stays server-side-only.

Name it `FOUNDRY_URL` and `import.meta.env.FOUNDRY_URL` is `undefined` — so `createClient` gets `undefined` as its base URL and you get an opaque network failure that looks nothing like a config problem.

**This is a safety feature, not an annoyance.** It's what stops you accidentally shipping a secret to the browser by adding it to `.env`. Which is also why the OAuth flow here uses a **public** client with no client secret: anything in a browser bundle is public by definition, and the PKCE flow is designed for exactly that.

Quick check when things are `undefined`:

```ts
console.log(import.meta.env);   // shows everything Vite actually exposed
```
</details>

## 7. Login flow

### Explain

```
   you open localhost:8080
        │
        ▼
   auth.getTokenOrUndefined()  ── have a token? ──▶ YES → render the app
        │ NO
        ▼
   auth.refresh()  ── refreshable? ──▶ YES → render the app
        │ NO
        ▼
   auth.signIn()  →  redirect to Foundry login
        │
        ▼
   Foundry redirects back to /auth/callback  ← must EXACTLY match
        │                                       Developer Console
        ▼
   token stored, app renders
```

```tsx
import { useEffect, useState } from "react";
import { auth } from "./foundryClient";

export function useLogin() {
  const [ready, setReady] = useState(false);

  useEffect(() => {
    if (auth.getTokenOrUndefined()) {
      setReady(true);
      return;
    }
    auth.refresh()
      .then(() => setReady(true))
      .catch(() => auth.signIn()); // redirects to Foundry login
  }, []);

  return ready;
}
```

### Exercise

Run `npm run dev -- --host 0.0.0.0 --port 8080` and open `http://localhost:8080`. You should be **bounced to your Foundry login page and then back**.

If you're not, diagnose it. There are only two possible causes.

<details>
<summary><b>Show solution</b></summary>

**If Checkpoint 1 fails, the problem is redirect URL mismatch or CORS — nothing else.** Don't debug your React.

**Redirect mismatch** — the URL in your code must match the one in Developer Console **exactly**, including:
- the scheme (`http` vs `https` — the A4 Option B fallback changes this!)
- the port
- the full path `/auth/callback`
- no trailing slash difference

Symptom: a redirect loop, or Foundry showing `invalid redirect_uri`.

**CORS** — see A4. Symptom: an error in the browser console containing the words "CORS policy".

Fastest way to tell them apart: **open the browser devtools Network tab.** A CORS failure shows the request going out and being blocked. A redirect mismatch shows Foundry rejecting you before any API call happens.
</details>

## 8. Read data

### Explain

```
   client(MyObject).fetchPage({ $pageSize: 25 })
          │              │
          │              └── returns { data: [...], nextPageToken }
          └── the generated, TYPED object type from your package

   Each row:  r.$primaryKey   ← built-in, always there
              r.someProperty  ← use the API NAME (see A2)
```

```tsx
import { useEffect, useState } from "react";
import { client } from "./foundryClient";
import { MyObject } from "<YOUR-GENERATED-PACKAGE-NAME>";
import type { Osdk } from "@osdk/client";

export function ObjectTable() {
  const [rows, setRows] = useState<Osdk.Instance<typeof MyObject>[]>([]);

  useEffect(() => {
    client(MyObject)
      .fetchPage({ $pageSize: 25 })
      .then(res => setRows(res.data));
  }, []);

  return (
    <table>
      <tbody>
        {rows.map(r => (
          <tr key={r.$primaryKey}>
            <td>{r.someProperty}</td>
            <td>{r.anotherProperty}</td>
          </tr>
        ))}
      </tbody>
    </table>
  );
}
```

### Exercise

Render a table of the same records your Workshop app shows. **That's the whole concept proven.**

Then handle three failure modes you'll probably hit: a property showing `undefined`, an empty table with no error, and a TypeScript type complaint.

<details>
<summary><b>Show solution</b></summary>

| Symptom | Cause | Fix |
|---|---|---|
| Property renders as `undefined` | You used the **display name**, not the API name | Back to A2 — Ontology Manager → property → API name |
| Empty result set, **no error at all** | Your user lacks permission on that object type, **or** the app's resource scope excludes it | Check your own permissions first (open the object in Object Explorer); then check the Resources page in Developer Console |
| `Type 'MyObject' is not assignable...` | You typed the state as `MyObject` | It must be `Osdk.Instance<typeof MyObject>` — `MyObject` is the *definition*, not an *instance* |
| `MyObject` isn't exported from the package at all | Object type wasn't selected on the Resources page | Add it, regenerate the SDK, `npm install` again |

The "empty, no error" one is worth internalising: **OSDK returns an empty page rather than a permission error.** Silence is a permissions symptom, not a code symptom.
</details>

## 9. Filter, link, aggregate

### Explain

```
   FILTER      .where({ status: { $startsWith: "OPEN" } })
   SORT        .fetchPage({ $orderBy: { createdAt: "desc" } })
   DATES       plain ISO 8601 STRINGS — no special type
               .where({ createdAt: { $gt: "2025-01-01T00:00:00Z" } })

   TRAVERSE A LINK
     ┌──────────┐   $link.relatedThings   ┌───────────────┐
     │ MyObject │ ───────────────────────▶│ RelatedThing  │
     └──────────┘                          └───────────────┘

   AGGREGATE   $select: { $count: "unordered" }
               $groupBy: { status: "exact" }
               → the count per status, computed server-side
```

```ts
// filter
client(MyObject).where({ status: { $startsWith: "OPEN" } }).fetchPage({ $pageSize: 20 });

// sort
client(MyObject).fetchPage({ $pageSize: 20, $orderBy: { createdAt: "desc" } });

// dates are plain ISO 8601 strings — no special type
client(MyObject).where({ createdAt: { $gt: "2025-01-01T00:00:00Z" } });

// traverse a link
const obj = await client(MyObject).fetchOne("pk-123");
const related = await obj.$link.relatedThings.fetchPage({ $pageSize: 50 });

// aggregate
const agg = await client(MyObject).aggregate({
  $select: { $count: "unordered" },
  $groupBy: { status: "exact" },
});
```

### Exercise

Add to your app: a filter box that narrows the table, a sort toggle, and a small "count by status" summary above the table using `aggregate`.

<details>
<summary><b>Show solution</b></summary>

```tsx
import { useEffect, useState } from "react";
import { client } from "./foundryClient";
import { MyObject } from "<YOUR-GENERATED-PACKAGE-NAME>";
import type { Osdk } from "@osdk/client";

export function ObjectTable() {
  const [rows, setRows] = useState<Osdk.Instance<typeof MyObject>[]>([]);
  const [counts, setCounts] = useState<Record<string, number>>({});
  const [filter, setFilter] = useState("");
  const [desc, setDesc] = useState(true);

  useEffect(() => {
    let query = client(MyObject);
    if (filter) {
      query = query.where({ status: { $startsWith: filter.toUpperCase() } });
    }
    query
      .fetchPage({ $pageSize: 25, $orderBy: { createdAt: desc ? "desc" : "asc" } })
      .then(res => setRows(res.data))
      .catch(err => console.error("fetch failed", err));
  }, [filter, desc]);

  useEffect(() => {
    client(MyObject)
      .aggregate({ $select: { $count: "unordered" }, $groupBy: { status: "exact" } })
      .then(agg => {
        const out: Record<string, number> = {};
        for (const bucket of agg) out[String(bucket.$group.status)] = bucket.$count;
        setCounts(out);
      });
  }, []);

  return (
    <>
      <input value={filter} onChange={e => setFilter(e.target.value)}
             placeholder="filter by status" />
      <button onClick={() => setDesc(d => !d)}>
        sort {desc ? "↓" : "↑"}
      </button>
      <div>{Object.entries(counts).map(([s, n]) => `${s}: ${n}`).join("  ·  ")}</div>
      <table>
        <tbody>
          {rows.map(r => (
            <tr key={r.$primaryKey}>
              <td>{r.status}</td>
              <td>{r.createdAt}</td>
            </tr>
          ))}
        </tbody>
      </table>
    </>
  );
}
```

**Two things worth noticing:**

- The **aggregate runs server-side**. It counts every matching object in the Ontology, not just the 25 on your page. Don't compute counts by fetching all rows and counting in JavaScript — that's the mistake this API exists to prevent.
- The filter re-runs the query rather than filtering the local array. Same reason: correctness at scale.

The exact shape of the `aggregate` response varies by OSDK version — `console.log` it once and adapt.
</details>

## 10. Write data with Actions

### Explain

You never write to an object directly. You **apply an Action**, which is a typed, permissioned, validated operation defined in the Ontology.

```
   your app                                  Ontology
   ┌────────────────────┐                   ┌──────────────────┐
   │ applyAction(       │                   │ updateStatus     │
   │   updateStatus,    │ ────────────────▶ │  ▸ validation    │
   │   { myObject:...,  │                   │  ▸ permissions   │
   │     newStatus:...} │                   │  ▸ writeback     │
   │ )                  │ ◀──────────────── │  ▸ audit trail   │
   └────────────────────┘   $returnEdits    └──────────────────┘
                                                     │
                                        Workshop app sees it too ✓
```

```ts
import { updateStatus } from "<YOUR-GENERATED-PACKAGE-NAME>";

await client(updateStatus).applyAction(
  { myObject: "pk-123", newStatus: "CLOSED" },
  { $returnEdits: true }
);

// validate without executing
await client(updateStatus).applyAction({ ...params }, { $validateOnly: true });

// bulk
await client(updateStatus).batchApplyAction([{ ...p1 }, { ...p2 }]);
```

```tsx
import { useState } from "react";
import { client } from "./foundryClient";
import { updateStatus } from "<YOUR-GENERATED-PACKAGE-NAME>";

export function StatusButton({ primaryKey, onDone }:
  { primaryKey: string; onDone: () => void }) {

  const [busy, setBusy] = useState(false);
  const [error, setError] = useState<string | null>(null);

  async function apply() {
    setBusy(true);
    setError(null);
    try {
      // dry run first — surfaces validation failures without writing
      const check = await client(updateStatus).applyAction(
        { myObject: primaryKey, newStatus: "CLOSED" },
        { $validateOnly: true }
      );
      console.log("validation result", check);

      await client(updateStatus).applyAction(
        { myObject: primaryKey, newStatus: "CLOSED" },
        { $returnEdits: true }
      );
      onDone();                       // refetch so the table updates
    } catch (e) {
      setError(String(e));
    } finally {
      setBusy(false);
    }
  }

  return (
    <>
      <button onClick={apply} disabled={busy}>
        {busy ? "saving…" : "Close"}
      </button>
      {error && <span style={{ color: "crimson" }}>{error}</span>}
    </>
  );
}
```

**Three things people get wrong here:**

1. **Not refetching.** The Action succeeds server-side but your local `rows` state is stale, so the UI looks broken. Call your fetch again (`onDone`) after a successful write.
2. **Passing the display name of an action parameter.** Same trap as A2 — parameter API names, always.
3. **Swallowing the error.** Action validation failures are informative; surface them. A silent `catch {}` here turns a clear "status transition not permitted" into "the button does nothing."

For a list of rows, prefer `batchApplyAction` over a loop of `applyAction` — one round trip instead of N.
</details>

## 11. Host it on Foundry

### Explain

Developer Console can host static frontends on a Foundry subdomain — no external hosting needed.

```
   npm run build  →  dist/
                       │
                       │  ⚠ zip the CONTENTS of dist/,
                       │    NOT the dist folder itself
                       ▼
              ┌────────────────────┐
              │ index.html         │  ← must be at the zip root
              │ assets/...         │
              └────────────────────┘
                       │
                       ▼
        Developer Console → Web hosting → upload
                       │
                       ▼
   https://<subdomain>.<enrollment>.palantirfoundry.com

   ⚠ then ADD that URL's /auth/callback as an ADDITIONAL redirect URL
     (the localhost one stays — you still want local dev to work)
```

> **Trap.** **Static assets only**, like GitHub Pages. No Node server, no SSR.

### Exercise

Build, zip and upload. Then work out why the hosted app bounces you into a redirect loop on first load — before reading the solution.

<details>
<summary><b>Show solution</b></summary>

**Because the hosted app's redirect URL isn't registered.** Your `.env.local` points at `http://localhost:8080/auth/callback`, and Developer Console only knows about that one.

Two things to fix:

1. **Add** `https://<subdomain>.<enrollment>.palantirfoundry.com/auth/callback` as an **additional** redirect URL in Developer Console. Don't replace the localhost one — you still want local dev.
2. **The built bundle needs the right value at build time.** `.env.local` is baked in by Vite during `npm run build`. So either use a separate `.env.production` with the hosted URL, or derive it at runtime:

```ts
const REDIRECT = `${window.location.origin}/auth/callback`;
```

The runtime version is better here: one build works in both places, and it's also what makes the app **auto-mappable when packaged for Marketplace** (see [B5, gotcha 3](#b5--the-gotchas-that-matter-in-interviews-and-in-production)).

The other common hosting failure is a **404 on every asset**, which means you zipped the `dist` folder instead of its contents — `index.html` must be at the zip root.
</details>

# Part B — Marketplace

## 12. What Marketplace actually is

### Explain

Marketplace is **how Foundry content moves between environments** — dev to prod, or one team to another.

The analogy that makes it click:

```
   Foundry DevOps  =  npm publish
   Marketplace     =  npm install
   Inputs          =  peer dependencies you must supply yourself
```

```
   ┌──── SOURCE ENVIRONMENT ────────────────────────────────────┐
   │                                                            │
   │  Foundry DevOps → build a PRODUCT                          │
   │   ┌──────────────────────────────────────────────┐         │
   │   │ OUTPUTS  (created on install)                │         │
   │   │  · Workshop app   · Ontology types           │         │
   │   │  · pipelines      · functions                │         │
   │   │  · Dev Console app                           │         │
   │   ├──────────────────────────────────────────────┤         │
   │   │ INPUTS   (installer must map these)          │         │
   │   │  · the raw source dataset(s)                 │         │
   │   └──────────────────────────────────────────────┘         │
   │            │  version it → publish to a STORE              │
   └────────────┼───────────────────────────────────────────────┘
                ▼
   ┌──── TARGET ENVIRONMENT ────────────────────────────────────┐
   │  Marketplace → pick product → MAP THE INPUTS to local data │
   │              → install → working copy, tracked as an       │
   │                INSTALLATION that can be upgraded           │
   └────────────────────────────────────────────────────────────┘
```

### Exercise

In your own words, and without looking: what's the difference between an **output** and an **input**, and why does the distinction exist at all?

<details>
<summary><b>Show solution</b></summary>

**An output is content the product *creates*** in the target environment — the Workshop app, the object types, the pipelines. You built these; they travel with the product.

**An input is a dependency the installer must *point at their own copy of*** — typically the raw source datasets. The product declares "I need an orders dataset shaped like this"; the installer says "here's mine."

**Why the distinction exists:** the product is the *logic*, not the *data*. Prod's orders dataset is not dev's orders dataset, and shipping dev data into prod would be both wrong and often illegal. Declaring the source as an input is what makes one product installable into many environments against different data.

The npm analogy holds precisely: outputs are the package's own files; inputs are peer dependencies the consumer must provide.
</details>

## 13. The five words

### Explain

| Term | Meaning |
|---|---|
| **Product** | A packaged bundle of Foundry resources |
| **Store** | A collection of products. **Local** (lives in a Project/folder) or **remote** (shared across enrollments) |
| **Output** | Content that gets created on install |
| **Input** | A dependency the installer must map to an existing resource |
| **Installation** | A **live instance** of an installed product, which can be upgraded |

```
   STORE
    └── PRODUCT (v1, v2, v3 …)
          ├── OUTPUTS  ──▶ created in the target
          └── INPUTS   ──▶ mapped by the installer
                │
                ▼
         INSTALLATION  ← a live thing, tracks a release channel,
                         can auto-upgrade when new versions publish
```

> **Trap.** "Installation" is the one people gloss over. It's not a past event — it's a **live object** with a release channel and an upgrade policy. That's the answer to "how do you push a fix to 20 deployments."

### Exercise

Cover the table. Define all five terms from memory, then check.

<details>
<summary><b>Show solution</b></summary>

Score yourself. The two most commonly fumbled:

- **Store** — people forget there are **two kinds**. A *local* store lives inside a Project you own (great for practice, and only needs Viewer to browse). A *remote* store is shared across enrollments. Which one you have determines whether B4 is available to you at all.
- **Installation** — people define it as "the act of installing." It's the **live instance**, which is why it can have a release channel, a maintenance window, and an auto-upgrade setting.

If you got Product / Output / Input right, you have enough to hold a conversation. Get Installation right and you can answer the operational follow-up question.
</details>

## 14. Install something

### Explain

Do this first — it takes **no permissions beyond Viewer**, and it teaches you the shape of the thing before you try to build one.

```
   1. Open Marketplace from the Foundry portal
   2. Search for a tutorial product
      (e.g. "Marketplace Getting Started Tutorial")
   3. Select "Create new installations", tick the product cards, confirm
   4. Map any required inputs        ← WATCH THIS SCREEN
   5. Choose the target Project
   6. Watch the installation job run, then open the installed resources
```

### Exercise

Install a tutorial product. As you go, note three things:

- **Which screen asks for inputs**, and what it's actually asking you to choose.
- **What the dependency graph looks like** — how much did it pull in that you didn't explicitly pick?
- **What appears in the target Project** afterwards.

<details>
<summary><b>Show solution</b></summary>

What you should have observed:

**The input-mapping screen comes *after* you pick the product and *before* you pick the target Project.** It's asking you to point each declared input at a resource *you already have*. If you have nothing suitable, the install can't proceed — which is exactly the peer-dependency behaviour from B1.

**The dependency graph is bigger than what you selected.** Picking a Workshop app pulls in the object types it displays, which pull in the datasets backing them, which pull in the pipelines producing those. This is the most instructive screen in the whole flow, and it's the same view you'll stare at in B4 when it shows you the *true* dependency graph of something you built and thought you understood.

**The target Project gets a folder of new resources**, and — the bit people miss — a tracked **Installation**, which is what you'd later upgrade. It is not a one-way copy.

If your install failed, the usual cause is `marketplace:use-resource-as-input` permission on the resource you tried to map (see [B5, gotcha 5](#b5--the-gotchas-that-matter-in-interviews-and-in-production)).
</details>

## 15. Build your own product

### Explain

This is the real exercise. Do it if **Foundry DevOps** appears in your portal.

```
   1. PREPARE      Workshop settings → enable "Installation configuration"
                   Run the PACKAGING ERROR LINTER first — it catches
                   unsupported constructs early.
                   ⚠ static/object-backed scenarios are NOT packageable

   2. CREATE       Foundry DevOps → New product → name it
                   → choose or create a LOCAL STORE (in a Project you own)

   3. ADD OUTPUTS  Add your Workshop app (Add files → navigate to it)
                   Add the Ontology object types + action types it uses
                   Optionally add your Dev Console OSDK app from Part A
                   ▸ DevOps AUTO-DETECTS dependencies — watch what it pulls in

   4. DEFINE       Your source dataset(s) become INPUTS
      INPUTS       The installer points these at their own data

   5. VERSION      Create a version → publish to the store
      & PUBLISH    ⚠ some stores require an approver ≠ the author

   6. INSTALL      Marketplace → find your product → install into a FRESH
                   Project → map the input dataset → verify it opens
                   and shows data

   7. BREAK IT     ← the best learning. See the exercise.
```

### Exercise

Complete steps 1–6. Then **deliberately break it**: rename an object type's **API name** in your source Ontology, republish, and reinstall.

Predict what happens to the OSDK app before you run it. Then explain why.

<details>
<summary><b>Show solution</b></summary>

**The OSDK app breaks.** The Workshop app may well survive.

**Why:** OSDK references Ontology entities **by API name**, and API names are **not remapped on install**. Your generated package contains `flightLeg`; the destination Ontology now has `flightSegment`; the lookup fails and the app can't find its object type.

Workshop tends to survive because it references entities by RID through the packaged mapping, not by API name in application code.

**This is the single most important thing in Part B**, and it's the [#1 gotcha](#b5--the-gotchas-that-matter-in-interviews-and-in-production) below. It is the mechanical explanation for "it worked in dev, broke in prod" — the phrase people say without being able to say *why*.

**The operational takeaway:** API names are part of your deployment contract across environments. Treat renaming one like renaming a public API — because that's what it is.

If DevOps isn't available to you, do B3 instead and read B5 twice. The vocabulary and the API-name gotcha are what people actually get asked about.
</details>

## 16. The gotchas

### Explain

**1. API names are not remapped on install.**

```
   AUTO-MAPPED ✓                   NOT MAPPED ✗
   ─────────────                   ────────────
   website URLs                    Ontology API names
   client IDs                      ↑
                                   entities must have IDENTICAL API names
                                   in source and destination, or the
                                   installed application breaks.

   ⚠ THE #1 CAUSE OF "it worked in dev, broke in prod"
```

**2. Developer Console apps package cleanly.** Packaging bundles metadata, OAuth client config (client type, grant types, redirect URLs) and resource restrictions. Installing auto-creates the Dev Console resource and configures OAuth on the target.

Two packaging styles:

| Style | Ships | Use for |
|---|---|---|
| **Application packaging** | the deployed website | production deployment |
| **Source code packaging** | the code repository as a template | bootcamps, standardised starters, or when the target needs its own Dev Console app |

**3. OSDK app packaging constraints.**

```
   □ package name must NOT contain "@" or a trailing "/sdk"
   □ OSDK version in package.json should be "latest" or "0.1.0"
     for the template to work out of the box
   □ auto-mapping of URLs/client IDs ONLY works if the app reads them
     from META TAGS IN index.html — not from bundled code

     apps scaffolded with @osdk/create-app v2.1.3+ or from a Foundry
     VS Code workspace already do this. Older apps need the meta tags
     added manually.
```

**4. Functions lose source visibility.** TypeScript V1 functions package as **executables with no viewable source** after install. Python and TypeScript V2 functions *do* include viewable source, but still can't be edited post-install in production mode.

**5. Permissions vocabulary.**

| Permission | Lets you |
|---|---|
| `marketplace:read-local-marketplace` | see a local store (Viewer role) |
| `marketplace:install-from-local-marketplace` | install products |
| `marketplace:use-resource-as-input` | needed on **every** resource used as an input |
| `marketplace:finalize-block-set` | approve/publish a version (store owners and editors) |

**6. Installation lifecycle.** Installations track a **release channel** and can be set to **auto-upgrade** when new versions publish, with maintenance windows. That's the operational answer to *"how do you push a fix to 20 deployments."*

### Exercise

Answer these four, then check:

**(a)** Your OSDK app installs fine but shows a blank screen and console errors about an unknown object type. Where do you look first?
**(b)** A colleague packaged an OSDK app from an old repo; after install it points at the *source* environment's Foundry URL. Why?
**(c)** Someone needs to be able to install products but not publish them. Which permissions?
**(d)** You've shipped a bug to 20 installations. How do you push the fix?

<details>
<summary><b>Show solution</b></summary>

**(a) API names.** Compare the object type's API name in the source Ontology against the destination. They must be identical; nothing remaps them. This is gotcha 1, and it should be your *first* hypothesis, not your fifth.

**(b) The app reads its config from bundled code, not from meta tags in `index.html`.** Auto-mapping of URLs and client IDs only reaches meta tags. An older scaffold hardcodes `VITE_FOUNDRY_URL` into the bundle at build time, so the installed copy keeps pointing home. Fix: add the meta tags manually, or re-scaffold with `@osdk/create-app` v2.1.3+.

*(This is also why the runtime `window.location.origin` trick from [A11](#a11--host-it-on-foundry-optional) is the better habit.)*

**(c)** `marketplace:read-local-marketplace` + `marketplace:install-from-local-marketplace`, plus `marketplace:use-resource-as-input` on whatever resources they'll map as inputs. **Withhold** `marketplace:finalize-block-set` — that's the publish/approve permission.

**(d) Publish a new version to the store.** Installations track a **release channel**; those set to auto-upgrade pick it up in their maintenance window. You don't touch 20 environments by hand — that's the entire operational point of Installations being live objects rather than past events.
</details>

## Troubleshooting Part A

| Symptom | Cause |
|---|---|
| CORS error in browser console | `localhost:8080` not in CORS policy → use the https fallback |
| Redirect loop / "invalid redirect_uri" | Redirect URL in code ≠ redirect URL in Developer Console. Must match **exactly**, including `/auth/callback` |
| `401 Unauthorized` on npm install | `FOUNDRY_TOKEN` not exported, or token expired |
| Object type not found in package | Not selected on the Resources page → add it and regenerate the SDK |
| Property is `undefined` | Using display name instead of API name |
| Empty result set, no error | Your user lacks permission on that object type, or the app's scope excludes it |
| TypeScript type mismatch | You need `Osdk.Instance<typeof MyObject>`, not `MyObject` |
