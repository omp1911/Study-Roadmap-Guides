# dbt Basics

Ten concepts, ten exercises, one dbt project that rebuilds the warehouse from guide 5.

**Environment:** [00-setup.md](00-setup.md) — the lab container, with `dbt-duckdb` installed and `warehouse/landing/*.csv` created.  
**Time:** about four hours.

**Do guide 5 first.** This guide builds the same bronze/silver/gold warehouse with dbt instead of hand-written SQL. Having done it by hand is what makes the tool make sense.

**What dbt is, in one line.** You write `SELECT` statements; dbt works out what order to run them in, creates the tables, and tests the results.

## 1. What dbt does

### Explain

In guide 5 you wrote `CREATE OR REPLACE TABLE silver.sales AS SELECT ...`. Every model had the same wrapper around it, you tracked the run order in your head, and the tests were a separate script you had to remember to run.

dbt removes all three.

```
   YOU WRITE                          DBT ADDS
   ┌────────────────────┐            ┌──────────────────────────────┐
   │ models/            │            │ CREATE OR REPLACE TABLE ...  │  the wrapper
   │   silver_sales.sql │  ────────▶ │ run order from ref()         │  the DAG
   │                    │            │ schema/database placement    │  the config
   │ SELECT * FROM ...  │            │ tests, docs, lineage         │  the extras
   └────────────────────┘            └──────────────────────────────┘

   one file = one model = one table or view
```

Three ideas carry most of the value:

| Idea | What it means |
|---|---|
| **A model is a SELECT** | One `.sql` file, one query, no DDL. dbt writes the `CREATE TABLE`. |
| **`ref()` builds the graph** | Reference another model by name and dbt infers the dependency and the order. |
| **Config is declarative** | Table or view, which schema, which tests — stated in YAML, not coded per model. |

dbt does **not** move data. It runs SQL inside a warehouse you already have. Here that warehouse is DuckDB; in a job it's usually Snowflake, BigQuery or Databricks, and almost everything you learn transfers.

> **Trap.** dbt is a transformation tool — the T in ELT. It doesn't extract, it doesn't load, it doesn't schedule. Those are other tools' jobs, and expecting dbt to do them is the most common source of early confusion.

### Exercise

You have this hand-written SQL from guide 5:

```sql
CREATE OR REPLACE TABLE gold.daily_category_revenue AS
SELECT CAST(sold_at AS DATE) AS sale_date, toy_category,
       sum(quantity * toy_price) AS revenue
FROM silver.sales GROUP BY 1, 2;
```

**(a)** Which parts of it would you *delete* when turning this into a dbt model?  
**(b)** Which part becomes a `ref()`?  
**(c)** Where does the choice of "table, not view" get expressed?

### Solution

**(a)** The entire first line. `CREATE OR REPLACE TABLE`, the name, and `AS` are dbt's job — the file name becomes the table name. What's left is the `SELECT` onward.

**(b)** `FROM silver.sales` becomes `FROM {{ ref('silver_sales') }}`. That's what tells dbt this model must run after that one.

**(c)** In a `config()` block at the top of the file, or in `dbt_project.yml` for a whole folder at once:

```sql
{{ config(materialized='table') }}

SELECT CAST(sold_at AS DATE) AS sale_date, toy_category,
       sum(quantity * toy_price) AS revenue
FROM {{ ref('silver_sales') }}
GROUP BY 1, 2
```

Notice there's no trailing semicolon and no `CREATE`. A dbt model is an expression, not a statement — dbt wraps it.

## 2. The project

### Explain

A dbt project is a folder with a config file and some SQL. Create it in the lab container:

```bash
cd /work
dbt init toyshop --profiles-dir /work/dbt --skip-profile-setup
```

Or just make the folders yourself — a working project needs surprisingly little:

```
   /work/toyshop/
   ├── dbt_project.yml       ← names the project, sets folder defaults
   ├── models/
   │   ├── staging/
   │   ├── silver/
   │   └── gold/
   └── /work/dbt/profiles.yml ← how to connect. lives outside the project.
```

**`profiles.yml` is separate on purpose** — it holds credentials, so it never belongs in the repo. `DBT_PROFILES_DIR` is already set to `/work/dbt` in your container, so dbt finds it without you passing a flag.

```yaml
# /work/dbt/profiles.yml
toyshop:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: /work/warehouse.duckdb
      schema: main
```

```yaml
# /work/toyshop/dbt_project.yml
name: toyshop
profile: toyshop
version: "1.0"

models:
  toyshop:
    staging: { +materialized: view,  +schema: bronze }
    silver:  { +materialized: table, +schema: silver }
    gold:    { +materialized: table, +schema: gold }
```

The `models:` block is where the medallion layers get expressed: **a folder per layer, with its defaults set once.** Any individual model can override them.

> **Trap.** `profile:` in `dbt_project.yml` must exactly match the top-level key in `profiles.yml`. When they differ you get `Could not find profile named 'x'` — which reads like a missing file and is nearly always a typo in one of these two lines.

### Exercise

Create the project and prove the connection works before writing any models. The command that checks configuration without running anything is `dbt debug`.

### Solution

```bash
mkdir -p /work/toyshop/models/{staging,silver,gold} /work/dbt
cd /work/toyshop

cat > /work/dbt/profiles.yml <<'YML'
toyshop:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: /work/warehouse.duckdb
      schema: main
YML

cat > dbt_project.yml <<'YML'
name: toyshop
profile: toyshop
version: "1.0"

models:
  toyshop:
    staging: { +materialized: view,  +schema: bronze }
    silver:  { +materialized: table, +schema: silver }
    gold:    { +materialized: table, +schema: gold }
YML

dbt debug
```

```
Connection test: [OK connection ok]
All checks passed!
```

**Run `dbt debug` first, always.** It separates "my configuration is wrong" from "my SQL is wrong", and those two failures look identical in the output of `dbt run` if you skip it.

## 3. Your first model

### Explain

A model is a `.sql` file in `models/`. The **file name becomes the table name**. No `CREATE`, no semicolon.

```
   models/silver/silver_sales.sql              →  silver.silver_sales
   models/gold/daily_category_revenue.sql      →  gold.daily_category_revenue

        file name ──────────────────────────────────▶ table name
        folder ─── (via dbt_project.yml) ───────────▶ schema + materialization
```

```sql
-- models/gold/toy_count.sql
SELECT count(DISTINCT toy_name) AS toys
FROM read_csv('/work/warehouse/landing/*.csv', header = true)
```

```bash
dbt run --select toy_count
```

Four commands cover almost everything:

| Command | Does |
|---|---|
| `dbt run` | Build all models |
| `dbt run --select my_model` | Build one |
| `dbt run --select my_model+` | That model and everything downstream of it |
| `dbt build` | Run **and** test, model by model, stopping at failures |

`dbt build` is the one to get in the habit of — it stops a broken model from feeding the twenty models beneath it.

> **Tip.** `dbt compile` writes the final SQL to `target/compiled/` without executing it. When a model does something inexplicable, read the compiled file — that's what actually ran, with every `{{ }}` resolved.

### Exercise

Write `models/gold/toy_count.sql` as above, run it, and then find the actual SQL dbt executed. Confirm the table exists in DuckDB.

### Solution

```bash
cd /work/toyshop
mkdir -p models/gold
cat > models/gold/toy_count.sql <<'SQL'
SELECT count(DISTINCT toy_name) AS toys
FROM read_csv('/work/warehouse/landing/*.csv', header = true)
SQL

dbt run --select toy_count
# 1 of 1 OK created sql table model gold.toy_count ... [OK in 0.05s]

cat target/run/toyshop/models/gold/toy_count.sql
```

The compiled file shows the wrapper dbt added:

```sql
create or replace table "warehouse"."gold"."toy_count" as (
  SELECT count(DISTINCT toy_name) AS toys
  FROM read_csv('/work/warehouse/landing/*.csv', header = true)
);
```

That's the whole trick — you wrote the inside, dbt wrote the outside.

```bash
python -c "import duckdb; print(duckdb.connect('/work/warehouse.duckdb').sql('SELECT * FROM gold.toy_count'))"
# 3
```

Two directories worth knowing apart: `target/compiled/` has the SELECT with Jinja resolved, `target/run/` has that plus the DDL wrapper. When debugging *your* logic, read `compiled/`.

## 4. ref and the DAG

### Explain

`{{ ref('other_model') }}` does two things at once: it inserts the right table name, and it tells dbt this model depends on that one. From those references dbt builds a **DAG** — a dependency graph — and derives the run order.

```
   stg_sales ──▶ silver_sales ──┬──▶ dim_toy
                                ├──▶ fct_sale
                                └──▶ daily_category_revenue

   You never state this order anywhere. dbt reads every ref() and works it out.
   Independent models run in parallel; dependent ones wait.
```

This is why you never hardcode a table name in a dbt model. `FROM silver.silver_sales` would work — and dbt wouldn't know the dependency exists, so it might build gold before silver and fail intermittently in a way that's miserable to diagnose.

| Selector | Builds |
|---|---|
| `--select silver_sales` | Just that model |
| `--select silver_sales+` | It and everything downstream |
| `--select +silver_sales` | It and everything upstream |
| `--select tag:gold` | Everything tagged `gold` |

> **Trap.** A circular `ref()` — A references B and B references A — fails with a cycle error at parse time. It always means two models want the same thing; the fix is a third model both can reference.

### Exercise

Write two models where the second depends on the first, then prove dbt worked out the order rather than following file order.

**(a)** `silver_sales` — the typed, deduplicated table from guide 5, concept 3.  
**(b)** `daily_category_revenue` — the gold aggregate, referencing (a).  
**(c)** Run only the gold model with `--select daily_category_revenue` and note whether silver rebuilds. Explain what you see.

### Solution

```sql
-- models/silver/silver_sales.sql
WITH typed AS (
  SELECT trim(receipt_no) AS receipt_no,
         CAST(sold_at AS TIMESTAMP) AS sold_at,
         trim(kid_name) AS kid_name, trim(kid_city) AS kid_city,
         trim(toy_name) AS toy_name, trim(toy_category) AS toy_category,
         CAST(toy_price AS DECIMAL(10,2)) AS toy_price,
         CAST(quantity AS INTEGER) AS quantity,
         trim(shop_name) AS shop_name, filename
  FROM read_csv('/work/warehouse/landing/*.csv',
                filename = true, all_varchar = true, header = true)
),
ranked AS (
  SELECT *, row_number() OVER (PARTITION BY receipt_no, toy_name
                               ORDER BY filename DESC) AS rn
  FROM typed
)
SELECT * EXCLUDE (rn) FROM ranked WHERE rn = 1
```

```sql
-- models/gold/daily_category_revenue.sql
SELECT CAST(sold_at AS DATE) AS sale_date,
       toy_category,
       sum(quantity * toy_price) AS revenue,
       sum(quantity) AS units,
       count(DISTINCT receipt_no) AS receipts
FROM {{ ref('silver_sales') }}
GROUP BY 1, 2
```

**(c)**

```bash
dbt run --select daily_category_revenue
# 1 of 1 OK created sql table model gold.daily_category_revenue
```

**Silver does not rebuild.** `--select X` means exactly X — dbt assumes its upstream tables are already there and current. This surprises people who expect a build tool to behave like `make`. When you want the upstream too, ask for it: `--select +daily_category_revenue`.

The dependency still exists and still matters; it governs *ordering* when both are in the run, not whether stale parents get refreshed.

## 5. Sources and staging

### Explain

Raw tables that dbt didn't create need declaring as **sources**. Then `{{ source('shop', 'raw_sales') }}` replaces the hardcoded name, and raw data appears in the lineage graph like everything else.

```
   sources.yml            staging model              rest of project
   ┌─────────────┐        ┌──────────────────┐       ┌────────────────┐
   │ shop.       │ ─────▶ │ stg_sales.sql    │ ────▶ │ every other    │
   │  raw_sales  │        │ rename, cast,    │       │ model uses     │
   └─────────────┘        │ nothing clever   │       │ ref() from here│
                          └──────────────────┘       └────────────────┘

   ONE staging model per source table. It is the only place that
   knows the source's column names.
```

```yaml
# models/staging/sources.yml
version: 2
sources:
  - name: shop
    schema: bronze
    tables:
      - name: raw_sales
```

The staging convention is the highest-value habit in dbt: **rename and cast in exactly one place.** When the source renames a column, you edit one file rather than every model that touched it.

| Staging does | Staging doesn't |
|---|---|
| Rename to your conventions | Join to other tables |
| Cast types | Aggregate |
| Trim, standardise case | Apply business rules |

> **Trap.** `source()` and `ref()` are not interchangeable. `source()` points at something dbt doesn't manage; `ref()` points at a model dbt builds. Using `source()` for a model you own breaks the dependency graph silently — no error, just wrong ordering.

### Exercise

Declare the landing CSVs as a source and add a `stg_sales` staging model that only renames and casts. Then confirm it appears in the lineage by running `dbt ls --select source:shop+`.

### Solution

Create the bronze table once, outside dbt — it's a load, not a transformation:

```bash
python -c "
import duckdb
con = duckdb.connect('/work/warehouse.duckdb')
con.execute('CREATE SCHEMA IF NOT EXISTS bronze')
con.execute('''CREATE OR REPLACE TABLE bronze.raw_sales AS
  SELECT *, now() AS _loaded_at
  FROM read_csv(\"/work/warehouse/landing/*.csv\",
                filename=true, all_varchar=true, header=true)''')
"
```

```yaml
# models/staging/sources.yml
version: 2
sources:
  - name: shop
    schema: bronze
    tables:
      - name: raw_sales
```

```sql
-- models/staging/stg_sales.sql
SELECT
  trim(receipt_no)                 AS receipt_no,
  CAST(sold_at AS TIMESTAMP)       AS sold_at,
  trim(kid_name)                   AS kid_name,
  trim(kid_city)                   AS kid_city,
  trim(toy_name)                   AS toy_name,
  trim(toy_category)               AS toy_category,
  CAST(toy_price AS DECIMAL(10,2)) AS toy_price,
  CAST(quantity AS INTEGER)        AS quantity,
  trim(shop_name)                  AS shop_name,
  _loaded_at
FROM {{ source('shop', 'raw_sales') }}
```

Then point `silver_sales` at `{{ ref('stg_sales') }}` and delete the casting from it — silver now only deduplicates, which is a single job rather than four.

```bash
dbt ls --select source:shop+
# source:toyshop.shop.raw_sales
# toyshop.staging.stg_sales
# toyshop.silver.silver_sales
# toyshop.gold.daily_category_revenue
```

That chain, derived entirely from `source()` and `ref()` calls, is the thing dbt is really selling.

## 6. Materializations

### Explain

A materialization is *how* dbt turns your SELECT into something in the warehouse. Four matter.

```
   view          CREATE VIEW           no storage, always fresh, recomputed per query
   table         CREATE TABLE          fast to read, rebuilt from scratch each run
   incremental   INSERT/MERGE new      only processes new rows
   ephemeral     inlined as a CTE      no object at all, just pasted into children
```

| Use | When |
|---|---|
| `view` | Staging models. Cheap, always current, rarely queried directly. |
| `table` | Silver and gold. Queried often, worth the rebuild. |
| `incremental` | Only when a full rebuild is genuinely too slow. |
| `ephemeral` | A CTE shared by two models that nobody needs to query. |

**Incremental** is the one with sharp edges. It needs a `unique_key` and an `is_incremental()` block that filters to new rows — and that filter is skipped on a first run or a `--full-refresh`:

```sql
{{ config(materialized='incremental', unique_key=['receipt_no','toy_name']) }}

SELECT * FROM {{ ref('stg_sales') }}

{% if is_incremental() %}
  WHERE _loaded_at > (SELECT max(_loaded_at) FROM {{ this }})
{% endif %}
```

`{{ this }}` is the model's own existing table. The `{% if %}` is what makes the same file work for both a first build and an incremental one.

> **Trap.** Start with `table` and change to `incremental` when a rebuild becomes too slow — not before. Incremental models drift from what a full rebuild would produce, and the debugging cost is real. `dbt run --full-refresh` rebuilds one from scratch; running that on a schedule is how you catch drift.

### Exercise

**(a)** Make `stg_sales` a view and `silver_sales` a table using `config()` blocks, overriding the folder defaults.  
**(b)** Convert `silver_sales` to incremental, keyed on `(receipt_no, toy_name)`.  
**(c)** Explain what `dbt run --full-refresh --select silver_sales` does differently, and why you'd ever want it.

### Solution

**(a)** At the top of each file:

```sql
{{ config(materialized='view') }}    -- stg_sales
{{ config(materialized='table') }}   -- silver_sales
```

**(b)**

```sql
{{ config(
     materialized='incremental',
     unique_key=['receipt_no', 'toy_name']
) }}

WITH ranked AS (
  SELECT *, row_number() OVER (PARTITION BY receipt_no, toy_name
                               ORDER BY _loaded_at DESC) AS rn
  FROM {{ ref('stg_sales') }}
  {% if is_incremental() %}
    WHERE _loaded_at > (SELECT max(_loaded_at) FROM {{ this }})
  {% endif %}
)
SELECT * EXCLUDE (rn) FROM ranked WHERE rn = 1
```

The `unique_key` is what makes dbt merge rather than append — without it, a re-sent row inserts a duplicate and you've rebuilt the guide 5 problem inside a tool that was supposed to prevent it.

**(c)** `--full-refresh` ignores the `is_incremental()` block and rebuilds the table from every row of source, exactly as `materialized='table'` would.

You want it when the model's logic changed (old rows were built with the old logic and won't update themselves), when you suspect drift, and on a schedule — weekly is common — as a correctness backstop.

## 7. Tests

### Explain

Guide 5's tests were queries that had to return zero rows. dbt's are the same idea, with the four most common ones reduced to a single word each in YAML.

```
   models/silver/schema.yml
   ┌────────────────────────────────────────┐
   │ models:                                │
   │   - name: silver_sales                 │      unique         no duplicates
   │     columns:                           │      not_null       no NULLs
   │       - name: receipt_no               │      accepted_values in a fixed set
   │         tests: [not_null]              │      relationships   FK resolves
   └────────────────────────────────────────┘
```

```yaml
version: 2
models:
  - name: silver_sales
    description: One row per toy per receipt.
    columns:
      - name: receipt_no
        tests: [not_null]
      - name: toy_category
        tests:
          - not_null
          - accepted_values: { values: ['Robots', 'Puzzles', 'Outdoor'] }
      - name: quantity
        tests: [not_null]
```

Anything more specific is a **singular test** — a `.sql` file in `tests/` containing a query that should return nothing:

```sql
-- tests/assert_gold_reconciles.sql
SELECT sum(revenue) AS gold_total
FROM {{ ref('daily_category_revenue') }}
HAVING sum(revenue) <> (SELECT sum(quantity * toy_price) FROM {{ ref('silver_sales') }})
```

Run with `dbt test`, or `dbt build` to interleave tests with the models as they're built.

| Test type | Lives in | Good for |
|---|---|---|
| Generic (`not_null`, `unique`) | `schema.yml` | Column-level rules, cheap to add |
| Singular | `tests/*.sql` | Anything involving two tables or arithmetic |

> **Trap.** A composite grain isn't covered by `unique` on either column alone. `unique` on `receipt_no` would *fail* on healthy data here, since one receipt legitimately has two toys. Test the pair with `dbt_utils.unique_combination_of_columns`, or write it as a singular test.

### Exercise

**(a)** Add generic tests: `receipt_no` not null, `toy_category` in the three known values.  
**(b)** Write the grain test — unique on the *pair* `(receipt_no, toy_name)` — as a singular test.  
**(c)** Write the reconciliation test from guide 5, concept 7.  
**(d)** Break something on purpose and watch a test fail.

### Solution

**(a)** As the YAML above.

**(b)**

```sql
-- tests/assert_silver_grain.sql
SELECT receipt_no, toy_name, count(*) AS n
FROM {{ ref('silver_sales') }}
GROUP BY 1, 2
HAVING count(*) > 1
```

**(c)**

```sql
-- tests/assert_gold_reconciles.sql
SELECT sum(revenue) AS gold_total
FROM {{ ref('daily_category_revenue') }}
HAVING sum(revenue) <> (SELECT sum(quantity * toy_price) FROM {{ ref('silver_sales') }})
```

**(d)** Remove `WHERE rn = 1` from `silver_sales` and rebuild:

```bash
dbt build
# FAIL 1 assert_silver_grain ......................... [FAIL 1 in 0.03s]
# Got 1 result, configured to fail if != 0
```

Note that `dbt build` stopped there rather than continuing into gold. With `dbt run` followed by `dbt test` you'd have built every downstream model on top of known-bad data before finding out — which is the whole argument for `build`.

## 8. Seeds

### Explain

A **seed** is a CSV in `seeds/` that dbt loads as a table with `dbt seed`. It's for small, hand-maintained reference data that belongs in version control:

```
   GOOD SEEDS                          NOT SEEDS
   category → department mapping       your actual sales data
   country codes                       anything over a few thousand rows
   a list of test store IDs            anything that changes daily
   holiday calendar                    anything with secrets in it
```

```
   seeds/toy_department.csv   →   dbt seed   →   a real table   →   ref('toy_department')
```

Seeds are referenced with `ref()`, exactly like models. dbt infers column types, and you can pin them in `dbt_project.yml` when the inference guesses wrong — which it does most often with leading-zero codes it decides are integers.

> **Trap.** Seeds are loaded by `dbt seed`, not `dbt run`. A model that refs a seed you haven't seeded fails with a missing-table error that doesn't mention seeds at all. `dbt build` runs seeds, models and tests together, which is one more reason to prefer it.

### Exercise

Create a seed mapping each toy category to a department, then a gold model that reports revenue by department.

| toy_category | department |
|---|---|
| Robots | Electronics |
| Puzzles | Games |
| Outdoor | Sports |

### Solution

```bash
mkdir -p /work/toyshop/seeds
cat > /work/toyshop/seeds/toy_department.csv <<'CSV'
toy_category,department
Robots,Electronics
Puzzles,Games
Outdoor,Sports
CSV

cd /work/toyshop && dbt seed
```

```sql
-- models/gold/department_revenue.sql
SELECT d.department,
       sum(s.quantity * s.toy_price) AS revenue
FROM {{ ref('silver_sales') }} s
JOIN {{ ref('toy_department') }} d USING (toy_category)
GROUP BY 1
```

```bash
dbt build --select department_revenue
```

**Worth adding a test here.** An inner join silently drops any category missing from the seed, so a new toy category would quietly vanish from the report. The `relationships` test catches exactly that:

```yaml
- name: toy_category
  tests:
    - relationships:
        to: ref('toy_department')
        field: toy_category
```

## 9. Snapshots

### Explain

Guide 1, concept 9 had you write SCD2 by hand — closing an old row and opening a new one whenever an attribute changed. dbt does it with a **snapshot**.

```
   Snapshot runs on Aug 1        Snapshot runs on Aug 3
   ┌──────────────────────┐      ┌────────────────────────────────────┐
   │ Ben | Toronto        │      │ Ben | Toronto     | Aug1 → Aug3    │  closed
   │                      │      │ Ben | Mississauga | Aug3 → ∞       │  current
   └──────────────────────┘      └────────────────────────────────────┘

   dbt adds: dbt_valid_from, dbt_valid_to, dbt_scd_id, dbt_updated_at
```

```sql
-- snapshots/kids_snapshot.sql
{% snapshot kids_snapshot %}
{{ config(
     target_schema='snapshots',
     unique_key='kid_name',
     strategy='check',
     check_cols=['kid_city']
) }}
SELECT DISTINCT kid_name, kid_city FROM {{ ref('silver_sales') }}
{% endsnapshot %}
```

Two strategies:

| Strategy | How it detects change | Use when |
|---|---|---|
| `timestamp` | An `updated_at` column moved | The source has a reliable one. Preferred. |
| `check` | Listed columns differ from last time | It doesn't. Slower but honest. |

**Snapshots only capture what they saw when they ran.** A value that changes twice between runs loses the middle state permanently. This is why snapshots run frequently and why they're the one dbt object you cannot rebuild from source.

> **Trap.** Never `--full-refresh` a snapshot. It drops the table and rebuilds it from current data — destroying every historical row, irreversibly. This is the most damaging single command in dbt.

### Exercise

Snapshot the kid → city relationship. Run it, change Ben's city in the underlying data, run it again, and show both the closed and current rows.

### Solution

```bash
mkdir -p /work/toyshop/snapshots
# write the snapshot file as above
cd /work/toyshop && dbt snapshot
```

Ben already appears twice in the source data — Toronto and Mississauga — so `SELECT DISTINCT` returns both and the snapshot can't tell which is current. Restrict it to one row per kid first:

```sql
SELECT kid_name, kid_city FROM (
  SELECT kid_name, kid_city,
         row_number() OVER (PARTITION BY kid_name ORDER BY sold_at DESC) AS rn
  FROM {{ ref('silver_sales') }}
) WHERE rn = 1
```

Then:

```bash
dbt snapshot   # first run: 3 rows, all open

python -c "
import duckdb
duckdb.connect('/work/warehouse.duckdb').execute(
  \"UPDATE silver.silver_sales SET kid_city='Hamilton' WHERE kid_name='Ben'\")"

dbt snapshot   # second run: Ben's Mississauga row closed, Hamilton row opened

python -c "
import duckdb
print(duckdb.connect('/work/warehouse.duckdb').sql('''
  SELECT kid_name, kid_city, dbt_valid_from, dbt_valid_to
  FROM snapshots.kids_snapshot WHERE kid_name = \'Ben\' ORDER BY dbt_valid_from'''))"
```

```
Ben | Mississauga | 2026-08-25 ... | 2026-08-25 ...   ← closed
Ben | Hamilton    | 2026-08-25 ... | NULL             ← current
```

`dbt_valid_to IS NULL` means current. That's the filter you'll write constantly against snapshot tables — and the reason `WHERE dbt_valid_to IS NULL` belongs in a view that other models use, rather than being repeated in each one.

## 10. Docs and lineage

### Explain

`dbt docs` turns your YAML descriptions plus the DAG into a browsable site — every model, its columns, its tests, its SQL, and an interactive lineage graph.

```bash
dbt docs generate
dbt docs serve --port 8080 --host 0.0.0.0
```

Then open `http://localhost:8080`.

```
   descriptions in schema.yml
              +                    ┌──────────────────────────────┐
   the DAG from ref()      ────▶   │  searchable model catalogue  │
              +                    │  column-level descriptions   │
   compiled SQL                    │  clickable lineage graph     │
                                   └──────────────────────────────┘
```

The lineage graph answers the two questions people actually ask: *where does this number come from* and *what breaks if I change this*. Both are otherwise archaeology.

A description is one line of YAML, and the discipline that matters is writing it while you write the model:

```yaml
models:
  - name: silver_sales
    description: One row per toy per receipt, deduplicated on re-sends.
    columns:
      - name: toy_price
        description: Price at time of sale, not current list price.
```

That `toy_price` description is the kind that earns its keep — it settles a question that would otherwise be asked every few months and answered wrong at least once.

> **Trap.** `dbt docs serve` binds to `127.0.0.1` inside the container by default, which your browser can't reach. Pass `--host 0.0.0.0`, and use port 8080, which is published for exactly this.

### Exercise

Add descriptions to your models and columns, generate the docs, and use the lineage graph to answer: **if the source renames `toy_price`, which models need changing?**

### Solution

```yaml
version: 2
models:
  - name: stg_sales
    description: Renamed and typed. One row per landing-file row, duplicates included.
    columns:
      - name: toy_price
        description: Price at time of sale, not current list price.
  - name: silver_sales
    description: One row per toy per receipt, deduplicated on re-sends.
  - name: daily_category_revenue
    description: Revenue, units and receipt count per category per day.
```

```bash
dbt docs generate
dbt docs serve --port 8080 --host 0.0.0.0
```

**Answer: only `stg_sales`.** That's the whole point of the staging layer — it's the single place that knows the source's column names, so a rename upstream is a one-file change. Everything downstream refers to *your* name for the column and is unaffected.

Confirm it from the command line rather than by eye:

```bash
dbt ls --select source:shop+ --output name
```

If more than one model would need editing, staging isn't doing its job — something downstream is reading the source directly.
